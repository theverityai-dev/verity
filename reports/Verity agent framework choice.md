# Keep Verity's agent loop, skip frameworks

**Verity should not adopt Mastra, LangGraph, Dify or CrewAI now.** The licence and maintenance facts in the ChatGPT recommendation are almost all correct. The conclusion drawn from them does not follow. Verity already runs a working, hand-rolled agent loop that does what a framework's "agent plus tools" layer would sell: typed tools generated from the Command and Query registry, filtered per user, executed as the calling human under `enforcePolicy()`, audited with `channel: "agent"`, grounded, and gated by a confirm step for destructive writes. The two things the recommendation treats as framework gifts are really Verity-owned problems: tenant isolation (INV-001, ADR-017, ADR-019) and the approval and trace record. A framework that persists its own threads, snapshots and traces would add a second tenant-scoped store outside RLS, which is the exact objection ADR-019 raised against Payload. Dify is ruled out for hosted Verity by its licence, which forbids multi-tenant operation without written authorization, and Flowise is dead. What Verity genuinely lacks is narrow: durable suspend and resume for pending approvals, server-side conversation and trace records, streaming, and a reliable paid model provider. All four can be built on the existing runtime. The recommended path is therefore to keep the loop, add a persisted pending-action table under RLS, define the six "agents" as tool bundles plus prompts, and write two new ADRs before any code. A framework earns another look only if multi-hour autonomous runs (Task 95 phases 4 to 6) are authorized. This report is built from five research notes dated 2026-10-24. Facts carry sources, and my own reasoning is marked **(inference)**. I did not see the pasted recommendation's text, only the claims listed in the brief.

Mastra's own history adds weight to the "first choice" doubt, which is a judgment I am drawing from sourced facts. On 2026-06-17 about 141 `@mastra/*` packages, including `@mastra/core`, were republished through a former contributor's npm account that still held publish rights, carrying an infostealer that targeted Windows, macOS and Linux ([Socket](https://www.socket.dev/blog/mastra-npm-packages-compromised); [Chainguard](https://chainguard.dev/unchained/mastra-npm-scope-takeover-143-packages-backdoored-via-compromised-contributor-account)). Counts in the literature range from 80 to 144. The framework code was not at fault, but the governance lapse is a signal, and Verity's developers work on Windows. The core package is also heavy: 83 MB unpacked with 30 runtime dependencies, against 8.4 MB for the Vercel AI SDK `ai` package and 4.6 MB for `@langchain/langgraph` ([npm](https://registry.npmjs.org/@mastra/core/latest)). Mastra's fast cadence means any pinned version is stale within weeks **(inference)**.

## Verity already owns the parts a framework would sell

Verity's agent is one TypeScript loop of about 400 lines in `agent-chat.ts`, calling any OpenAI-compatible chat-completions endpoint over plain `fetch`, with the explicit comment "No SDK dependency added" ([agent-chat.ts](file:///D:/Code/verity/src/server/platform/agent-chat.ts)). `package.json` contains no AI package at all, only `zod` v4, and a repo-wide search found that no framework has ever been evaluated ([package.json](file:///D:/Code/verity/package.json)). Tools come from `buildToolManifest`, which converts every registered Command and Query to a JSON Schema and includes it only if the actor's role grants the verb and the capability is ready for the tenant ([tool-manifest.ts](file:///D:/Code/verity/src/server/platform/tool-manifest.ts)). Every call runs through `executeCommand` or `executeQuery` as the caller's own `ActorContext` (ADR-017), the channel is "recorded, never consulted" ([policy.ts](file:///D:/Code/verity/src/server/platform/policy.ts)), and agent writes require that every `*Id` input first appeared in a query result that turn ([grounding.ts](file:///D:/Code/verity/src/server/platform/grounding.ts)). Task 113 audited all of this and found no drift ([Task 113](file:///D:/Code/verity/taskplans/113_ai_implementation_audit_all_clients_and_global_agent.md)). The weaknesses recorded in the repo are on the provider side: the Groq free tier caps at 8,000 tokens per minute (less than one grounded multi-tool turn), `gpt-oss-120b` is unreliable at forced tool calls, and the full 104-tool owner manifest costs about 18,000 tokens. None comes from a missing orchestration framework **(inference)**.

The six agents map onto this directly **(inference)**. The existing `toolKeys` narrowing, already used by the Outreach insights caller, is the mechanism for a persona: each of the six is a named bundle of tool keys plus a system prompt, and narrowing also fixes the 18,000-token manifest problem. The business analyst is the read-query persona and matches Task 95's "Business Reasoning" phase. Quotation, procurement and project coordination follow DSEW's enquiry, quote, order, BOM, procurement, stages and dispatch chain ([DSEW PRD](file:///D:/Code/verity/clients/dsew/prd.md)). The closest shipping analogue is Dynamics 365's Supplier Communications Agent, which reads supplier emails and PDFs, matches them to the purchase order, and flags the change for a buyer to approve ([Microsoft Learn](https://learn.microsoft.com/en-us/dynamics365/supply-chain/procurement/procurement-agent-supplier-com-overview)). The document agent is Task 95 Phase 5 (multimodal), which is unbuilt. Stylified needs a persona only for the owner or supervisor, since its workers have no phones ([flow.md](file:///D:/Code/verity/clients/stylified/flow.md)), and neither client has asked for any agent. DSEW's recalculated quote removed AI entirely ([DSEW proposal](file:///D:/Code/verity/clients/dsew/proposal/README.md)), and Task 120 assigns WhatsApp and conversational commerce to Relay, a separate product that calls Verity's tool surface ([Task 120](file:///D:/Code/verity/taskplans/120_relay_verity_integration.md)).

The three rules deserve an honest audit, because the recommendation assumes a framework supplies them. Tenant isolation is the strongest: the agent runs as the human, tenant context is server-derived, and tools carry no tenant parameter to inject **(inference, matching OWASP's "complete mediation" guidance)** ([OWASP LLM06](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)). Human approval is only partly met. Destructive commands never run from the agent, and two or more calls to the same routine command stop at a preview, but a single routine write runs immediately without a prompt ([agent-chat.ts](file:///D:/Code/verity/src/server/platform/agent-chat.ts)). The preview lives only in client state, so it is lost when the dock closes. That falls short of the OWASP requirement to have a human approve high-impact actions, and of what Microsoft, SAP and NetSuite ship (see the OWASP and vendor evidence in the security note). Traceability is also partial: agent actions appear in the audit trail labelled `agent`, but conversations and prompt and response content are not persisted server-side ([Task 84](file:///D:/Code/verity/taskplans/84_verity_ai_agent_system.md)). One more point cuts against autonomy. On tau-bench, GPT-4o scored 61% on one retail attempt but 25% when required to succeed on all eight ([Sierra](https://sierra.ai/de/blog/tau-bench-shaping-development-evaluation-agents)), though those are 2024 models and current ones likely score higher. Anthropic's own guidance is to prefer predefined workflows for well-defined tasks. The shape that fits Verity is deterministic commands doing the work, with the model proposing, extracting and explaining.

## Frameworks add a second tenant store and solve a gap Verity can close itself

The only genuine capability gap a framework would fill is durable suspend and resume. Verity's workflow engine records per-step transactions and idempotency keys, but `WorkflowRunStatus` has only Running, Succeeded and Failed, the job runner is deliberately synchronous, and there is no queue ([schema.prisma](file:///D:/Code/verity/prisma/schema.prisma); [job.ts](file:///D:/Code/verity/src/server/platform/job.ts)). Role-based approval chains (`ApprovalRequest`, `ApprovalStep`) already exist as tenant-scoped tables. A pending agent action is, in the thin-loop view, just a row such as `AgentPendingAction { tenantId, actorId, toolName, input, inputHash, expiresAt }` under the same RLS as everything else, and the approve endpoint re-runs `enforcePolicy()` as the approving human and executes through the normal write path **(inference, aligned with HumanLayer's 12-factor agents, factors 5 to 8)** ([12-factor-agents](https://github.com/humanlayer/12-factor-agents)). Anthropic's tool-runner docs say the same at the API level: for human-in-the-loop approval, "use the manual loop instead" ([Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-runner)).

Each framework's storage collides with the rules in `CLAUDE.md`. Mastra auto-creates `mastra_*` tables for threads, messages, workflow snapshots, traces and scorers, with no tenant column and no RLS awareness; it scopes by `resourceId` and `threadId`, enforced only when middleware sets reserved request-context keys ([PostgresStore reference](https://mastra.ai/reference/storage/postgresql); [request context](https://mastra.ai/docs/server/request-context)). Two options follow, and both are bad **(inference)**. If the tables get a GUC-keyed policy, every Mastra query returns nothing, because its pool never sets `verity.tenant_id`. If they get no policy, they become a second isolation surface with fail-open application checks. The workable route is a separate Postgres schema with `disableInit`, plus a custom tenant-aware storage adapter running inside `withTenant()`, which Mastra does not provide. Mastra's default pool of 20 connections is also the shape that caused Verity's production `EMAXCONNSESSION` outage on a 15-connection project pool, and behaviour under pgbouncer transaction mode (port 6543) is undocumented. LangGraph.js has the same problem: its Postgres checkpointer writes its own tables via its own pool with `thread_id` and `checkpoint_ns` but no tenant column, and a production postmortem reports a checkpoint table growing to 40 GB in six weeks with no retention policy ([LangGraph persistence](https://docs.langchain.com/oss/javascript/langgraph/persistence); [postmortem, secondary and unverified](https://pub.towardsai.net/langgraph-checkpointing-is-not-free-a-production-postmortem-398bc86861f4)). Any adoption would be a new ADR under ADR-019's "no second tenant-isolation mechanism of any kind" rule before code, per the stop conditions in `CLAUDE.md`.

Approval primitives deserve a closer look because a framework's version can be weaker than it looks. Mastra's approval is storage-backed and resumable, and its `requireToolApproval` function form can see request context ([approval docs](https://mastra.ai/docs/agents/agent-approval)), but `approveToolCall({ runId })` checks no permission by itself, so Verity's endpoint would still own who may approve. The Vercel AI SDK 7 carries approvals in a client-held message array, which is why it added HMAC signing and then patched a flaw where a signature could verify against a different tool call ([Vercel blog](https://vercel.com/blog/ai-sdk-7); [ai@7.0.36](https://newreleases.io/project/github/vercel/ai/release/ai@7.0.36)). OpenAI's `RunState.fromString` does not authenticate the snapshot ([OpenAI Agents JS](https://openai.github.io/openai-agents-js/guides/human-in-the-loop/)). In every case Verity would treat the client's approval as an intent and resolve it against a server-side row **(inference)**. That is the design the thin loop starts from. If a library is ever wanted, the lighter and cleaner-licensed candidates are the AI SDK as a model and streaming layer only, or LangGraph.js (MIT, 4.6 MB), and Mastra is the heaviest of the three **(inference)**. Even the AI SDK has churn: v5, v6 and v7 arrived within about a year, with `needsApproval` renamed `toolApproval`, and a secondary source says v7 is ESM-only on Node 22 or later.

The Python and low-code options fail on separate grounds. Pydantic AI and CrewAI are Python, so Verity would run them as a separate service reached over HTTP, the pattern ADR-027's amendment set for Laya, with a signed per-request actor token, no database credentials, and the ADR-029 posture of manifest-only tools and no destructive commands **(inference)**. TypeScript with Zod already provides schema-validated output, so Pydantic mainly adds a second schema language. Dify's licence blocks the hosted case: one workspace per Verity tenant is what the clause forbids, and one shared workspace would make Dify a second isolation surface and break INV-001. For DSEW's single tenant the licence might permit it, but the default stack is about ten containers and at least 4 GiB ([Dify README](https://github.com/langgenius/dify)), roughly doubling operational surface on a target the plan sizes at 4 vCPU and 16 GB. Flowise has no upstream and unpatched workspace-authorization flaws, and its own stated reason for shutting down was that coding agents beat rigid low-code flows.

## DSEW's no-LLM rule and the local-model question

The research notes disagree on how settled the DSEW position is. The product-owner decision is Task 129 D3 (2026-10-22): never run a language model on the DSEW host, ship Mode B with AI off and zero egress, and if DSEW opts in, call a hosted OpenAI-compatible endpoint through one allow-listed route as the caller's own `ActorContext`; a local model is considered only on a separate GPU machine and only if asked ([Task 129](file:///D:/Code/verity/taskplans/129_architecture_honesty_demo_readiness_and_dsew_onprem.md)). ADR-054 clause 6 restates this, but ADR-054 is still PROPOSED and awaiting owner review ([adr-054.md](file:///D:/Code/verity/verity-spec/17_decisions/adr/adr-054.md)). The TypeScript-alternatives note cited the rule from project memory only, while the repo note read the primary text. The two notes also frame it differently. The security note says CPU-only 16 to 32 GB servers run 3 to 4B models at roughly 7 to 20 tokens per second but reach only about 20% on multi-turn tool calling (Qwen3-4B-Instruct-2507 on BFCL multi-turn, [benchmarklist](https://benchmarklist.com/benchmarks/bfcl_v3_multiturn/)), and the benchmark hardware is mixed, so figures vary two to three times. That supports D3 on quality grounds without reopening it. A local model is viable only for single-shot drafting or schema-constrained extraction feeding a deterministic proposal, never for sequencing ERP commands **(inference)**. The server survey that would settle CPU and RAM is unanswered, and DSEW's host runs Windows Server 2019, so Node-version requirements for any new dependency (for example the AI SDK's reported Node 22 floor) must be checked before adoption.

India's data law adds a minimisation argument that holds regardless of framework. The DPDP Rules were notified 13 November 2025 with most obligations from 13 May 2027, and cross-border transfer is permitted unless a country is blacklisted ([Hogan Lovells](https://www.hoganlovells.com/en/publications/indias-digital-personal-data-protection-act-2023-brought-into-force-); [Truyo](https://truyo.com/?p=8832)). One Mondaq item puts cross-border provisions in force immediately and an Outlook Business piece claims in-country storage is mandatory; both conflict with the law-firm sources and the latter probably conflates sectoral rules. Employee data (names, wages) sent to a hosted model makes the provider a sub-processor, so tools should send IDs, quantities and aggregates and resolve names server-side. Claude in-country inference via Amazon Bedrock India and OpenAI India data storage are both reported but only in press **(inference: verify at procurement)**.

## The recommended path

**Keep.** Keep `agent-chat.ts`, the manifest, grounding, `executeCommand` as the only write path, ADR-017's rule that `channel` is never an authorization input, and the "no SDK" stance. Keep `toolKeys` as the persona mechanism. Keep destructive-never-from-agent.

**Add, in this order.**
1. Before anything else, accept or amend ADR-054 (still PROPOSED), because the DSEW AI posture depends on it. Reconcile the stale `CLAUDE.md` entries: ADR-029 is shown PROPOSED but the ADR file says ACCEPTED 2026-09-30, and ADR-031 is listed under both ACCEPTED and PROPOSED.
2. Fix the provider side first, since it caused every recorded failure: pick a paid, tool-calling-reliable OpenAI-compatible model with an adequate token budget, and hand-roll streaming over the existing `fetch` call (a small change, and the AI SDK is not needed for it).
3. Write ADR A, "agent runs, pending actions and conversation records", before code. It would cover a tenant-scoped `AgentPendingAction` and conversation and tool-call trace tables under RLS and `withTenant`, retention, what content is stored, and an approval policy by impact class. Build the table, an approve endpoint that re-runs `enforcePolicy()` as the approver, and an expiry job on the existing cron.
4. Close the single-write gap by deciding which routine writes may run without a prompt (see open decisions), and make every agent-proposed write that fails that test create a pending action instead of running.
5. Write ADR B, "general-purpose LLM calls from capabilities and untrusted-content ingestion". ADR-027 explicitly defers this decision. It would cover per-tenant egress opt-in, data minimisation for DPDP, treating supplier PDFs, emails and WhatsApp text as untrusted (the EchoLeak and ForcedLeak lesson), no outbound rendering channel, and no write tools in a turn that read untrusted content without confirmation.
6. Then build the personas as tool bundles, starting with the read-only business analyst, then document extraction producing proposed commands (procurement and quotation), keeping the DSEW chain in mind. Defer quality and project coordination until a client asks.
7. Add an evaluation harness (a pass-all-k style test over the persona prompts) before widening tool sets.

**Revisit a framework only on a trigger.** The trigger is owner authorization of Task 95 phases 4 to 6 (proactive or unattended agents), which ADR-017 says needs its own ADR. Before choosing then, extend Verity's own workflow engine with a Waiting status, since that is the true missing primitive. If a library is still wanted, run a bounded spike of LangGraph.js or the AI SDK against the tenant-storage test (a custom adapter inside `withTenant()`, tested under the 6543 pooler) rather than adopting Mastra by default. Whichever is chosen: exact version pins, a committed lockfile, `npm ci --ignore-scripts`, a package-age cooldown, and a CI guard against importing from any `ee/` path.

**Do not pursue.** Dify (licence, footprint), Flowise (dead), a Python agent service on the DSEW host, and a local model on the DSEW host.

## Where the notes disagree or run out

Several disagreements and gaps affect how much to trust specific points. The Mastra note says Mastra builds on the Vercel AI SDK per a third-party article, while its own dependency list shows only the provider specification packages (v5, v6 and v7), not the `ai` package. Funding dates conflict (April versus 15 May 2026), and compromised-package counts run from 80 to 144. LangGraph's JS (1.5.2) and Python (1.2.17) versions are separate lines, and third parties disagree on the Plus price ($35 versus $39; the official page says $39). The DPDP cross-border timing conflict is noted above. The Mastra note could not retrieve its own post-incident statement, Snyk, or the Hacker News threads. Open technical gaps: Mastra's table definitions, whether `PostgresStore` or `PostgresSaver` works under pgbouncer transaction mode, Mastra's telemetry opt-out (`posthog-node` is a core dependency), traced bundle size on Vercel, and whether the AI SDK's ESM-only Node 22 requirement is official. Benchmarks are 2024 to 2025 models; no 2026 or manufacturing-specific numbers were found. The repo note did not read Tasks 88, 90 and 91 in full, did not read the Stylified PRD or the DSEW meeting deck for AI asks, and did not confirm whether `executeQuery` writes an audit row for every read. The Odoo, NetSuite and Zoho vendor comparisons rest partly on partner and press material. The OWASP LLM01 primary page was not fetched.

## Open decisions for the product owner

1. Approve or reject "no agent framework now", including whether the "no SDK dependency" stance in `agent-chat.ts` stays as policy.
2. Define the approval policy: which routine agent writes may run immediately, which must create a pending action, and whether a single write ever skips confirmation. This is currently undefined and is the biggest gap against rule two.
3. Authorize ADR A (durable pending actions, conversation and trace records) and decide retention and what content may be stored, given DPDP.
4. Authorize ADR B (general LLM calls and untrusted-content ingestion) and decide the per-tenant egress opt-in model.
5. Decide whether the six personas are authorized work at all, since the 2026-09-30 scope note authorizes only Tasks 118, 119 and 120 and new capability work needs owner approval. Pick which one first, and for which client.
6. Accept, amend or reject ADR-054, and confirm whether Task 129 D3 stands as written, including its separate-GPU-machine option for DSEW.
7. Choose the model provider and budget, and whether India-region inference is a requirement for any client.
8. Decide whether Stylified or DSEW want any agent feature before a demo, given the DSEW quote removed AI and Stylified's flow has none.
9. Decide how Verity's in-product agent relates to Relay (Task 120), so conversational and WhatsApp work is not built twice.
10. Decide the trigger and sponsor for Task 95 phases 4 to 6, and whether a Waiting status in Verity's workflow engine is the first step.
11. Approve a supply-chain policy for any new dependency (exact pins, lockfile, `--ignore-scripts`, cooldown), independent of this decision.
12. Clean up `CLAUDE.md` so ADR-029 and ADR-031 statuses match their ADR files.

## Conclusion

The research changes the question. "Which framework?" assumed the agent layer was missing, but Verity's agent layer exists and is constitutionally constrained in ways frameworks are not built to respect. The decisive tests are who owns tenant-scoped state and who decides authorization, and every candidate fails the first by default. The substantive work is a short list of Verity-owned items: a persisted approval record, a stated approval policy, a trace record, a reliable provider, and two ADRs. Doing these first also gives any future framework spike a precise acceptance test (a tenant-aware storage adapter that survives transaction-mode pooling), which is more useful than a feature checklist. The riskiest assumption in the original recommendation is that adding agents is mostly a tooling choice. For this ERP it is mostly an authorization, evidence and scope decision, and those belong to the product owner.
