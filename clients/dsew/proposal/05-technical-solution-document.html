Section 1

Summary for DSEW management and IT

Verity is a modular business operating platform. For DSEW it is configured as an engineering and manufacturing ERP that traces each engineered, one-off product from enquiry through approved drawing, bill of materials, manufacture and testing to dispatch. It runs on one Linux virtual machine on DSEW's own premises, with nothing leaving DSEW's network by default.

The server-load answer in one paragraph

Verity is not a heavy system. It is one application process and one database, sized for a four-core, 16 GB VM and not a data centre. User devices carry no processing load. Report generation, file indexing and any AI indexing run as scheduled background work outside office hours, with limits so that a heavy job can never starve interactive users. DSEW's other workloads on the same Hyper-V host are protected by fixed CPU and memory allocation to the VM. A load test against agreed response-time targets on DSEW's actual VM is a go-live gate.

Section 2

Design principles for a customer-hosted system

Most business software is built to run in a vendor's cloud, where capacity can be added at will. A system that runs on the customer's own server has the opposite constraint: the hardware is fixed, it is shared with other work, and the customer's IT team carries the operational risk. Verity's deployment design for DSEW follows eight principles.

#PrincipleWhat it means for DSEW's server
1Small, known footprintA fixed set of five services on one VM, each with a memory budget (section 6). There is no message-broker cluster, no search cluster and no second database engine to feed.
2Server does the work, device displaysOffice PCs, phones and tablets render pages and capture input. Nothing computational is pushed to them, so old or low-end devices work.
3Interactive work firstAnything slow (reports, exports, indexing, backups, AI) runs as scheduled background work with concurrency limits and runs outside shift hours by default.
4Bounded queriesEvery list is paginated and indexed. No screen loads an unbounded table. Search is database-indexed.
5Fail closedIf tenant context or permission is missing, queries return nothing and writes are rejected. A fault never widens access.
6Everything can be put backScripted backup, tested restore, versioned upgrades with rollback. Recovery is rehearsed before go-live, not merely described.
7Data stays on the premisesNo cloud service is required to run, and none receives DSEW data by default. Outbound access is needed only for install and update, and can be replaced by offline media.
8Standardise the foundation, configure the behaviourIdentity, permissions, audit, numbering, workflow and storage are one shared foundation. DSEW's specific behaviour is configuration and modules on top, so later additions do not require redevelopment.

Section 3

Solution architecture

Verity is built as layers. Each layer has one job, and an upper layer cannot bypass the one below it. This is what allows new capabilities to be added later without redesigning the foundation.

3.1 Runtime components

ComponentTechnologyRole
ApplicationTypeScript, Next.js, ReactServes the interface and the permissioned API. Runs the business logic: commands, queries, state transitions, rules and events
DatabasePostgreSQL 16System of record. Row-level security enforces company isolation. Holds records, audit trail, the event log and full-text indexes
IdentityKeycloak (OpenID Connect)Sign-in, password policy, optional multi-factor sign-in, session lifetime. Application roles remain in Verity
File storageS3-compatible object storeDrawings, certificates, reports, photographs. Held on a separate volume so file growth never competes with the database
Reverse proxyStandard TLS-terminating proxyHTTPS, compression, static-asset caching, rate limiting, security headers
PackagingDocker and ComposeReproducible install; versioned images; scripted upgrade and rollback
SchedulerBuilt in, one triggerRuns background work (reminders, escalations, reports, indexing, backups) on a schedule with concurrency limits

3.2 Path of a single request

  1. The user's device sends an HTTPS request carrying a signed session issued after Keycloak sign-in.
  2. The application derives the company (tenant) context from the authenticated session, never from anything the browser sends in the request body.
  3. For a change, the request becomes a command. One policy gate checks the user's permission (action, entity, scope) and the record's current state.
  4. Inside one database transaction the tenant is set, the state change is written, the audit entry and event are recorded, and the transaction commits or rolls back as a whole.
  5. For a read, a query returns only the rows that tenant and scope permit; the database applies the same filter even if the application code were wrong.
  6. The response returns a small payload. Large lists are paged; files are streamed from the object store.

3.3 Extension model

A new capability is registered, not patched in. It declares its entities, workflows, permissions, events, screens and the other capabilities it depends on. DSEW's later additions (a new product family, an inspection format, a new department) are configuration or added modules; the foundation, the workflow engine and the authorisation model are not modified, and no code is forked per client.

Section 4

Verity platform specification

This section defines the platform foundation on which all 19 modules rest. These are the building blocks that make the system consistent, auditable and extensible.

4.1 Identity and data model

4.2 Authorization

  • Permissions are Verb + Entity + Scope. For example approve · Quotation · Organization or release · BillOfMaterials · Tenant. There are no hard-coded roles such as "manager" in the code; roles are named sets of permissions that DSEW defines.
  • Scopes narrow where a permission applies: tenant-wide, one organization, or one location. Additional axes such as team or resource are handled by configuration.
  • One decision point. Every command, from the screen, the API, a scheduled job or an AI assistant, passes the same policy check. There is no back door and no elevated service path.
  • Separation of duties is configurable: DSEW chooses who drafts, reviews, approves and releases, and whether self-approval is ever allowed.
  • The AI channel acts as the calling user. Whatever an AI feature does, it does with that user's own permissions and nothing more (section 13).

4.3 State and transition

Business records move through configurable state machines. Every state belongs to one of six behavioural categories, so reports and timers can read behaviour without depending on DSEW's own labels.

CategoryMeaningExample DSEW states
DraftBeing prepared; not yet in forceQuotation draft, BOM draft
PendingWaiting for a decision or inputAwaiting approval, awaiting material
ActiveIn progressIn winding, in assembly, in testing
BlockedCannot proceed until a condition clearsOn hold for NCR, awaiting drawing revision
CompletedExecution finished (terminal)Tested and passed
CancelledAbandoned (terminal)Enquiry lost, order cancelled

Completed and Closed are different. Completed means the work is done. Closed is an administrative step that makes the record permanently read-only. A closed record cannot be edited; later rework creates a linked child record. This is how "what was approved is what was built" is enforced by the system and not by habit.

4.4 Commands, queries, events and audit

CommandA request to do something: create a quotation, release a BOM, issue material. Validated, authorised, state-checked and applied in one transaction
QueryA read of current state, always tenant-scoped and permission-scoped
EventA fact that something happened (BOM released, inspection failed). Other modules and notifications react to events, so modules stay loosely coupled
ProjectionA derived read view (dashboards, ageing, stock balance) built from events and records
Audit trailFor every change: who, what, when, from which channel, previous and new values. Written in the same transaction as the change; the application cannot alter or delete it
Failed attemptsRefused commands are recorded as metadata, so repeated denied attempts are visible to the administrator

4.5 Rules, workflow and configuration

  • Workflow definitions are data: nodes (steps), edges (transitions) and conditions (for example "approval required above a value", "all mandatory checks passed").
  • Custom fields add DSEW-specific attributes (kVA rating, impedance, cooling class, customer drawing number) to any record without schema forks.
  • Document numbering is configurable per document type with prefix, year, site and sequence, allocated safely under concurrent use so numbers are never duplicated.
  • Forms and tables are generated from metadata, so adding a field or a column is configuration with permission, validation and audit already applied.
  • Print templates produce DSEW's branded quotation, traveller, challan, packing list, certificate and report formats.
  • Capability activation: modules are switched on per tenant, and version pins mean DSEW upgrades on its own schedule.
  • Nothing DSEW-specific is hard-coded. Test templates, inspection checklists, approval workflows, manufacturing routes, teams, roles, report and print formats, notification rules, categories and master data are settings held as data and edited by DSEW's administrators, with permission and audit applied. The fixed foundation (tenant isolation, sign-in, the permission check, the audit trail, the closed-record rule) is not configurable by design. The full list and its boundary are in document 1, section 2.

4.6 Application programming interface

A permissioned REST API exposes the same commands and queries the screens use, under the same policy gate. DSEW can read its data programmatically for reporting. No external system integration is included in scope (document 1, section 4).

Section 5

Installable web application (PWA) and device reach

Verity is delivered as a Progressive Web App. It opens in any modern browser, and on any device it can also be installed with one tap so it behaves like a native application, with no app store, no per-device installer and no separate mobile build to maintain.

5.1 Why this matters for DSEW

One build, every device

The same application serves office PCs, tablets and shop-floor phones. There is no Android build, iOS build and Windows build to keep in step, so every user sees the same version on the day it is upgraded.

Zero client installation work

Users open an internal address and choose "Install". IT does not push software to devices. Removing it is just as simple, and a lost phone holds nothing once its session is revoked.

Light on the device

Pages are server-rendered and compressed, so a modest phone or an older office PC performs well. The installed app is a shortcut to the same web application, not a second copy of the system.

Light on the server

The application shell, fonts, icons and scripts are cached on each device after the first visit. Later visits fetch only data, which cuts repeated traffic and CPU work on DSEW's server.

5.2 What is delivered

DSEW will host Verity on its own server, so the load Verity places on that server is a design requirement, not an afterthought. This section sets out where load comes from, how it is held down, how much of the VM each part may use, and how it is proven before go-live.

Reports and dashboardsAggregations over many recordsPrecomputed projections refreshed in the background; heavy reports queued to run off-hours; result caching

6.6 Protecting DSEW's other workloads

  • Fixed allocation: the VM is created with static memory and a defined number of virtual processors, so Verity cannot take more of the host than agreed.
  • Disk separation: database, files and backups are on separate volumes, so file growth or a backup cannot starve database input and output.
  • Quiet background: backups, indexing and large reports run in a scheduled window that DSEW sets, at low priority.
  • Visibility: a health view for the administrator shows CPU, memory, disk, database size, queue depth and slow queries, with alert thresholds, so capacity is a managed number and never a surprise.
  • Growth path: if DSEW outgrows the VM, resources are increased on the same architecture. There is no re-platforming.

Section 9

Security and data protection

Security is part of the foundation. It is applied to every operation from the first release, not added as a layer afterwards.

9.1 Controls by layer

LayerControl
TransportTLS for all traffic; HTTP redirected to HTTPS; modern protocol versions only; security headers (content security policy, frame protection, referrer policy)
AuthenticationKeycloak with password policy and lockout; optional multi-factor sign-in, enabled on request; configurable session lifetime and idle timeout; immediate session revocation
AuthorizationVerb + Entity + Scope permissions checked on the server for every command; no reliance on hidden screens; one policy gate for all channels
Tenant isolationCompany context comes from the authenticated session, never from the request. Row-level security in PostgreSQL enforces isolation even if application code were wrong; with no scope set, queries return nothing and writes are rejected
Database accountThe application connects as a least-privilege account that cannot bypass row-level security. Start-up refuses a privileged account. A separate account is used only for schema migration
AuditAppend-only trail of every change with actor, time, channel and before/after values; cannot be edited or deleted by the application
Input handlingServer-side validation; parameterised queries; output encoding; protection against cross-site request forgery; upload type and size checks
SecretsHeld in a protected environment file (restricted permissions, owned by a named administrator), never in the database or in source. A sealed offline copy is held by DSEW's owner
FilesAccess through the application's permission check; files are not publicly addressable
BackupsEncrypted at rest on the backup target; restore tested
DiskFull-disk encryption recommended on the VM and backup target, confirmed at acceptance
Network exposureOnly the HTTPS port is exposed. Database, identity and object store are bound to the VM's internal network and not reachable from the LAN
Software supplyPinned, versioned releases; dependency vulnerability review at each release; tested upgrade and rollback
Support accessRemote, time-limited, audited, and only with DSEW's permission

9.2 Rule for every change to data

For each state-changing operation the design records: who is acting, the permission required, the scope, the preconditions, the state change, the audit entry, the event emitted, and the behaviour on failure. A change that cannot answer all eight is not released.

9.3 AI and data protection

Nothing leaves DSEW's server to an external AI service unless DSEW explicitly enables that service. Local AI features run inside the signed-in user's own permissions, so a user can never retrieve through AI what they could not open directly. AI is never an approver and never changes a record on its own (section 13).

9.4 Scope boundary

Independent penetration testing and statutory certification are outside this scope. They can be arranged separately.

10.4 Upgrades and rollback

  1. Release notes and the changes to DSEW's installation are shared in advance.
  2. A backup is taken automatically before the upgrade.
  3. The upgrade is applied with database migrations in a defined order.
  4. Health checks confirm the new version. If they fail, the scripted rollback restores the previous version and data state.
  5. Upgrades are applied at a time DSEW chooses, typically outside working hours.

Section 12

Engineering, manufacturing and quality controls

DSEW builds engineered, one-off products. The central requirement is that what was approved is what is built, and nothing leaves the factory without its checks. Verity enforces this through five connected controls.

12.1 From enquiry to dispatch: the controlled chain

12.2 The five controls

ControlHow it works
Revision lockA released drawing or BOM revision cannot be edited. A change creates a new revision through the approval path. A job records the revision it was built to.
Approval separationDrafting, review, approval and release are different permissions. DSEW decides whether one person may hold more than one.
Quality gateA failed or missing mandatory inspection or test blocks quality release. An NCR closes only after CAPA verification. Dispatch is blocked until release.
Immutable evidenceMeasured values, photographs and signatures are stored as evidence that cannot be altered, with the user, time and device.
Closed means closedWhen a job or order is closed, it is permanently read-only. Rework is a new linked record, so history is never rewritten.

12.3 Traceability

Each finished unit carries a QR identity. Scanning it opens the unit's record: the sales order, BOM revision, components with batch or heat numbers, route and operations, inspection and test results, and dispatch details. A forward trace answers "which units used this batch"; a backward trace answers "what went into this unit". An optional public verification page shows a controlled subset for the customer.

12.4 Stock integrity

Inventory is a ledger: every receipt, issue, transfer and adjustment is a posted entry. Corrections are made by reversal with a reason, never by silently changing a balance, so the quantity on hand can always be explained from its history.
