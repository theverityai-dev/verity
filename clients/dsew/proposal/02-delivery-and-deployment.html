04How we work

Specification and design

A signed specification (workflows, roles, numbering, templates, formats, the agreed depth of every module and acceptance criteria), an architecture and database overview, and approved mock-ups.

Milestones and acceptance

DSEW has 5 business days after each demonstration or delivery to accept it or report material deviations. In-scope defects are corrected and shown again before sign-off. No report in that period means accepted. Payment milestones are in document 1, section 8.

Issue tracking

A shared issue list visible to DSEW from day one, with severity, owner and status. Critical (wrong data, security issue, or work blocked with no workaround) and High (major function impaired) issues block go-live.

UAT

Scripts agreed in advance: enquiry to quotation to order; BOM release; material to job; failed test blocking dispatch; dispatch released after approval; data export; backup and restore. Each scenario is signed off with date, tester and result.

Definition of done

Server-side authorisation, tenant-isolation test, audit entry, validation and error states, automated tests, documentation note, demonstrated in the review.

Module dependencies

Numbering and approval precede BOM release; a released BOM precedes material planning, manufacturing orders and travellers; test templates precede dispatch gating; stock and invoicing data precede finance and dashboards.

Changes: anything beyond the agreed scope needs a written change request with a revised cost or schedule, approved before work. Remote first: delivery is remote; on-site work and travel are chargeable separately and need prior approval.

05Environments

  • Company-hosted test environment: demonstrations and early hands-on use.
  • One DSEW Linux VM: installed at kickoff, used for UAT, and used as production only after the gates pass. A second production VM is not included. If the surveyed host cannot support this, a different arrangement is quoted separately.

06Go-live gates

None of the gates below has been completed yet. They are passed with DSEW, on DSEW's host, before production use.

  1. Server survey complete and the DSEW host confirmed suitable.
  2. Installation and HTTPS access work on the DSEW host, including a real-phone upload.
  3. Combined backup and restore of database, files and identity configuration onto a clean environment passes.
  4. Identity-provider and object-store outage behaviour tested: existing sessions keep working, new sign-ins or uploads fail clearly, quality gates stay enforced.
  5. UAT scripts pass.
  6. The data export reconciles with the system.

Go-live happens when these gates pass and the handover is signed. The testing period (monthly, for as long as DSEW chooses) starts on that date.

Pre-deployment compatibility check

The hosting environment has not been tested. Before anything is installed on DSEW's host, we run a non-intrusive check in the first days after kickoff and record pass or fail for each dependency. Nothing on the host is changed during it.

07Running on Windows Server 2019

Verity runs on Linux. We do not propose running it natively on Windows Server 2019, and we do not recommend Docker Desktop or WSL for production there. The plan is one Ubuntu Server VM under the Hyper-V role on your server, or a small dedicated host. This has not been tested on your server. Licensing of the Windows host is for your Microsoft partner.
