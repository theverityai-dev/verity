# Architectural Decision Record

## ADR-036: Failed commands are recorded as metadata, and HQ reads only totals

* **Decision ID**: ADR-036
* **Status**: ACCEPTED (2026-10-09), decided by the engineering lead under the product owner's
  standing instruction to take open decisions from project context (Task 125 item 7.4).
* **Question**: HQ audit A6 asks for a platform-wide "something is broken" view with failed commands.
  ADR-013 forbids a fourth cross-tenant projection without a decision. Is a failed-commands view
  allowed, and what may it show?
* **Context**: Today a command that throws is rolled back and leaves no row, so no list of failures
  exists in any tenant, let alone across tenants. The HQ overview already shows per-client health
  counts (ADR-034) through one `SECURITY DEFINER` function that returns counts and never rows.
* **Decision**:
  1. **Record the failure, not the request.** When a command throws, a row is written in a new
     tenant-scoped, append-only table `command_failure` in its own transaction after the command's
     rollback: command key, error code (`E_VALIDATION`, `E_FORBIDDEN`, `E_INTERNAL`...), acting user
     id, channel, correlation id, time. **Never the input payload, never the message text** (it can
     carry a guest's name or a figure).
  2. **HQ reads totals only.** One `SECURITY DEFINER` function returns, per client and per command key
     and error code, a count and the latest time over a window. It returns no row ids, no user ids
     and no free text. This is the same shape and the same reasoning as the ADR-034 health columns.
  3. **The client sees its own failures in full metadata** through ordinary `enforcePolicy()` reads
     on `command_failure` (Read on a new `verity.platform.command_failure` entity).
  4. Validation and permission refusals are counted but flagged `expected`; the "needs attention"
     list uses only `E_INTERNAL` and repeated refusals of one command by one user.
* **What this is not**: not a cross-tenant read of business rows, not a change to INV-001, ADR-017,
  ADR-034 or `enforcePolicy()`. An operator who needs the detail of one failure enters the client
  (ADR-035) and reads it there through the client's own RLS.
* **Consequences**: a migration (new table, definer function, entity row), a write in the command
  runtime's failure path that must not itself fail the response, and a conformance entry in the
  append-only list. Retention follows the audit tables. **Built 2026-10-09:** migration
  `20261009050000_command_failure` (table, append-only trigger, `verity.operator_command_failures`, grant
  backfill for tenant administrators), `recordCommandFailure` in `execution-failure.ts` called from the command
  runtime's failure path only (queries and page refusals are not recorded), the client's "Failed commands"
  section on the Audit page, and the HQ "Needs attention" reasons. Open: an installation-wide retention rule.
