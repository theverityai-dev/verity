# Architectural Decision Record

## ADR-055: Agent actions run in approval classes; confirm-class actions are stored, tenant-scoped, single-use records; every agent turn leaves a bounded record

* **Decision ID**: ADR-055
* **Status**: ACCEPTED (2026-10-24). Extends ADR-017 (the agent acts as the calling human); supersedes nothing. Decided under the
  product owner's delegation of 2026-10-24 ("decide for me"). The thresholds in clause 5 are the author's initial choice and may
  be changed by the product owner without a new ADR.
* **Question**: The chat agent (`agent-chat.ts`, Task 84) runs a routine write the moment the model asks for it, shows a preview
  only when one message holds two or more calls to the same command, and keeps that preview in the browser. The browser then posts
  the command key and the inputs back to the server to confirm. Nothing about a turn is stored except the ordinary audit row of
  each command it ran. Task 113 found no drift from ADR-017; the research of 2026-10-24
  (`reports/Verity agent framework choice.md`) found these three gaps: approval is partial, the pending state is client-held,
  and a turn cannot be reconstructed. What approval rule applies, where does a pending action live, and what is recorded?
* **Context** (read 2026-10-24):
  * OWASP LLM06:2025 (Excessive Agency): few, specific tools; run in the user's context; human approval for high-impact actions;
    authorization enforced downstream, "rather than relying on an LLM to decide if an action is allowed".
  * Every agent-framework option examined keeps pending approvals in its own store (Mastra `mastra_workflow_snapshot`, LangGraph
    checkpointer) with no tenant column, or in client-held state (Vercel AI SDK 7), and in each case the client's "approve" is
    only an intent. Verity already has the right store: a tenant table under RLS, written through `withTenant()`.
  * `runCommandBatch` already refuses destructive commands unless `confirmed` is passed, and `executeCommand` re-runs
    `enforcePolicy()` for every call, so executing a stored action as the proposer re-checks permission and current business
    rules at the moment of execution, not at the moment of proposal.
* **Decision**:
  1. **Four approval classes**, computed for a command in one place (`src/server/platform/agent-approval.ts`):
     * `read`: a query. Runs immediately.
     * `routine`: a command that is none of the below. Runs immediately. The person's current message is the authorization,
       exactly as clicking the same button would be.
     * `confirm`: a command that moves or records money, posts to the ledger, cancels, voids, reverses, approves, issues,
       dispatches, releases, closes, merges, bulk-edits, imports, or sends or publishes outward. It is never executed from a
       model tool call. It is stored as a pending action and runs only on the proposer's explicit Confirm.
     * `blocked`: a destructive command or a `Delete` verb. Unchanged from ADR-017's implementation: never run from the agent,
       answered `E_NEEDS_APPROVAL`, and the person does it in the app. Allowing it to be *proposed* is a separate decision for the
       product owner after the pending-action store has run in production (Review).
     Classification errs toward `confirm`: an over-flagged command costs one click, an under-flagged one can move money. A registry
     test fails when a command whose name carries a money or outbound word is not `confirm`, and when any destructive command is not
     `blocked`.
  2. **The two or more calls to one routine command rule stays**, now as a pending action rather than client state.
  3. **A pending action is a tenant-scoped row** (`agent_pending_action`, RLS enabled and forced, INV-001) holding the proposer,
     the command key, the exact inputs, a human-readable summary, a status (`pending | approved | rejected | expired`), an expiry
     (30 minutes after proposal) and, once decided, a bounded outcome (counts and per-item error codes, never full results).
     * Only the proposer may decide it. The agent is the person (ADR-017); a different user confirming it would be a different
       authorization decision and is out of scope.
     * Deciding is an atomic compare-and-set on `status = 'pending' AND expires_at > now() AND actor_id = <caller>`. A double click,
       a replayed request or two tabs run the action at most once.
     * Execution is `runCommandBatch(actor, command, storedInputs, { channel: "agent" })` as the proposer. Inputs are never
       re-derived from the model and never accepted from the client again; the client sends only the pending action's id.
     * At proposal time every `*Id` input must satisfy the turn's grounding cache (Task 84 area 4). A proposal that fails is
       refused with `E_UNGROUNDED` and no row is written.
  4. **Every agent turn leaves a record** (`agent_turn`, RLS enabled and forced): actor, channel, the user's message, the reply,
     each tool call as key, kind, ok, inputs and a bounded summary of the output (2,000 characters), any pending action it
     created, the model name and the duration. Not stored: the system prompt, full tool results, the provider's key, or other
     users' history. The record is written best-effort after the reply is computed and never blocks or alters the reply.
  5. **Retention**: turn records 90 days, decided pending actions 30 days after the decision or expiry, both purged by a daily
     platform schedule. They cascade with the tenant. No read surface is added by this ADR; the records exist for incident
     reconstruction and are reachable only under RLS.
* **Constraints**:
  1. This ADR changes no invariant, no grant, no role and not `enforcePolicy()`. ADR-017 stands: `channel` is recorded, never an
     authorization input. The one behaviour the channel changes remains a restriction (grounding, and now `confirm` and
     `blocked`), never an added authority.
  2. A pending action authorizes nothing by existing. Execution always goes through the ordinary command pipeline as the proposer.
  3. No agent framework owns this state (ADR-056).
  4. Turn records may hold personal data typed by the user. They are tenant data under INV-001, bounded by clause 5, and carry no
     data from outside the caller's own tenant.
* **Consequences**:
  * Task 84's `PendingPreview` becomes a thin view of a stored row. The browser stops posting inputs; the route accepts a
    pending action id.
  * `confirm`-class commands stop being runnable by prompt injection alone: a poisoned record can at most create a pending row the
    person sees, with its summary, and must click.
  * A new command is `routine` unless its name or verb matches; the registry test is the guard against a quiet miss.
* **Review**: reopen when (a) the store has run in production for 90 days with the metrics of Task 131 phase F, to decide whether
  `blocked` commands may be proposed; (b) a second user is needed to approve (an approval chain through `ApprovalRequest`); or
  (c) Task 95 phase 4 to 6 (unattended agents) is authorized, which needs its own ADR under ADR-017.
