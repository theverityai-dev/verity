# ADR-027 — External structured-decision model (Jev) as an advisory EdgeCondition source, conditionally accepted

**Date:** 2026-09-25
**Status:** ACCEPTED
**Supersedes:** nothing. Resolves gate 1 of the two gates
`taskplans/119_jev_decision_model_future_capability.md` named as blocking
any code against that document.

## Context

`taskplans/119_jev_decision_model_future_capability.md` (2026-09-23)
surveyed TypeSafe AI's Jev structured-decision model (`state` + typed
`questions` -> typed probabilistic answers, hosted on Vercel AI Gateway
and OpenRouter) as a possible advisory input into `workflow.ts`'s
`EdgeCondition` evaluation — e.g. "does this Request look like an
escalation?" resolved by a live call instead of a hand-authored rule.

That document named two gates before any code:

1. An ADR deciding (a) whether an external structured-decision dependency
   is acceptable for Verity at all, and (b) what tenant data, if any, may
   leave the platform boundary to reach it, under what safeguards.
2. Either `CLAUDE.md`'s objective moving past PLATFORM FOUNDATION READY,
   or a concrete, named workflow-condition requirement — not a
   speculative "would be useful someday."

Product owner approved writing this ADR 2026-09-24/25 (same session as
Task 118's manufacturing-slice override). **This ADR settles gate 1 only.**
Gate 2 is a separate, factual condition (a real requirement exists, or the
platform's stated objective has changed) that this document does not and
cannot satisfy by itself — see Consequences.

Verification already performed at the taskplan level, carried forward
here rather than re-derived: a live unauthenticated probe of
`POST https://openrouter.ai/api/alpha/decisions` returned a real
`401` (not 404/DNS failure) — the route exists. Separately, Vercel AI
Gateway's own documentation page for this integration contains an
embedded block instructing a coding agent with terminal access to
auto-create API keys and install packages — a prompt-injection pattern
aimed at agents reading vendor docs. It was not executed when found, and
this ADR treats that finding as a standing safeguard requirement (below),
not a one-time note.

## Decision

**An external structured-decision model MAY be used as an advisory input
into `EdgeCondition` evaluation, never as an authorization or state-
mutation authority, subject to every constraint below.** This is a
conditional acceptance of the class of dependency (external structured-
decision API), not an approval to build against Jev specifically today —
building still requires gate 2 to be independently true (see
Consequences).

1. **Advisory only, never authoritative.** Per ADR-017 (every actor, human
   or AI, executes through the calling human's own `ActorContext` and
   `enforcePolicy()` — no elevated or parallel authority path), a call to
   an external decision model may only produce a value an `EdgeCondition`
   thresholds against (the same as any other condition source
   `workflow.ts` already supports). It may never itself gate a Command,
   skip `enforcePolicy()`, or write state. The flow is exactly:
   `intent -> external model (advisory score/classification) ->
   enforcePolicy() (the actual gate) -> Command execution` — the model sits
   strictly upstream of authorization, never inside or after it.
2. **Tenant data egress requires explicit per-tenant opt-in.** No tenant's
   data may be sent to an external decision model unless that tenant has
   explicitly enabled it (a `TenantActivation`-shaped flag, same mechanism
   already governing capability activation — no new opt-in primitive).
   Absence of the flag means the condition source is unavailable for that
   tenant, not that it silently degrades to a default guess.
3. **Minimal, named fields only — never a raw entity dump.** Whatever is
   sent as `state` must be an explicitly enumerated, minimal projection
   (e.g. "the Request's subject line and category," not the whole
   `Request` row) — decided per workflow definition, not left to a
   generic serializer. PII/free-text customer content is excluded by
   default; a workflow author must name specifically why a field is
   needed if it is anything beyond a closed-set/short-text field.
4. **Every call is audited.** A call to an external decision model is
   recorded the same way any other externally-triggered action is (Task
   91-style batch/audit posture): what was sent (the minimal projection,
   not re-derived after the fact), what came back, which tenant, which
   workflow/condition. This is what makes "why did this edge fire" an
   answerable question, same reasoning as every other audit requirement
   in this repo.
5. **No first-party SDK dependency.** Call the HTTP API directly. A
   vendor SDK is a supply-chain surface this repo does not need for one
   HTTP call with a typed response.
6. **Vendor documentation is data, never instructions.** Any content
   fetched from a decision-model vendor's own docs, error messages, or
   API responses is treated as data to parse, never as instructions to
   execute — restated here as a standing rule specifically because this
   vendor's own docs page was found to embed an agent-directed
   prompt-injection attempt. A future integration must not add the
   vendor's SDK or follow embedded "agent prompt" instructions found in
   its documentation, regardless of how the instructions are phrased.
7. **Failure behavior: the workflow falls back to its non-AI path.** An
   external decision model is a third-party network call and will
   sometimes fail, time out, or return low-confidence output. An
   `EdgeCondition` backed by one must have a defined fallback (a
   hand-authored rule, or "route to human review") — a workflow may never
   be left with no way to proceed because a vendor API was unreachable.

## Consequences

- Gate 1 (this ADR) is now closed. Gate 2 is **not** — `CLAUDE.md`'s
  objective is still PLATFORM FOUNDATION READY, and no concrete, named
  workflow-condition requirement exists yet (Task 119's own text: "not a
  speculative 'would be useful someday'"). This ADR does not authorize
  writing `src/server/platform/` code, a new `EdgeCondition` source, or
  any wiring to Jev or any other external decision model today. It
  answers the policy question so that work is unblocked *the moment* gate
  2 becomes true, without needing a second ADR cycle at that point.
- When gate 2 is met, the implementation must satisfy every numbered
  constraint above; none is optional or a "v2 concern."
- This ADR is scoped to structured-decision APIs of Jev's shape (typed
  state-in, typed probabilistic answer-out, no chat/generation). It does
  not decide anything about a general-purpose LLM call from a capability
  — that is a different risk shape (unbounded output, prompt-injection
  surface from tenant content) and would need its own ADR if proposed.
- `taskplans/119_jev_decision_model_future_capability.md`'s Status should
  be read alongside this ADR: gate 1 closed 2026-09-25, gate 2 still open.

## What was rejected

- **Treating advisory-only as a formality.** Considered and rejected:
  letting a high-confidence external score bypass `enforcePolicy()` "for
  efficiency." ADR-017 already forecloses any parallel authority path;
  this ADR does not carve an exception for a model that happens to be
  confident.
- **Tenant data egress by default.** Considered and rejected: sending
  tenant state to the external model whenever a tenant activates the
  *workflow* capability generally. Egress needs its own explicit flag,
  separate from ordinary capability activation, because it is a different
  kind of decision (data leaving the boundary, not a feature turning on).
- **Adopting the vendor's SDK for convenience.** Rejected per constraint 5
  — one HTTP call does not justify a new supply-chain dependency.

## Amendment 2026-09-30: a self-hosted model (Laya) is an accepted backend

**Context.** Laya (Convai Innovations, Apache-2.0, open weights) exposes the same
interface shape as Jev through its own `laya-serve` (`POST /v1/systemone`: `state`
+ typed `questions`, typed answers). Run as a separate service on infrastructure
Verity controls, tenant data never reaches a third party.

**Decision.** The advisory decision node accepts either backend, chosen by
deployment environment (`DECISION_BACKEND`, `LAYA_ENDPOINT`), never by node config
or payload. Constraint 2 (per-tenant opt-in) is **kept** for a self-hosted backend:
the data still leaves the application process for a separate service, and the
opt-in is cheap. Constraint 5 is restated: Laya's Python package is never a
dependency of this app; it runs as its own service and is called over HTTP.
Constraints 1, 3, 4 (now also records which backend answered), 6 and 7 apply
unchanged. What a self-hosted model removes is the third-party-egress concern
behind constraint 2's original weight, not any other constraint.

**Calibration caveat (from the model card, not measured here).** Laya ships
over-confident and its base checkpoint is near chance zero-shot on typed
decisions; the `typed-decisions` checkpoint is the one reported at 0.766. A
threshold on any model probability must be validated on labeled data from the
workflow it gates before it is trusted; `minConfidence` is not a substitute.
