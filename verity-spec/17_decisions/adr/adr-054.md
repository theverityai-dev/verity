# Architectural Decision Record

## ADR-054: Hosted is the default; DSEW is the one Mode B validation target; Modes C and D are parked

* **Decision ID**: ADR-054
* **Status**: ACCEPTED (2026-10-24). Amends ADR-031 (supported deployment modes); supersedes nothing. Decided in direction by the
  product owner's request of 2026-10-22 (Task 129). Accepted 2026-10-24 when the product owner delegated the open decisions
  blocking the AI-agent work ("decide for me"); the text is unchanged from the PROPOSED draft. Clause 6 is the rule ADR-055 and
  ADR-056 rely on for on-premises hosts.
* **Question**: Verity can be run as hosted multi-tenant SaaS (Vercel and Supabase), as an on-premises package (ADR-031 Modes A, B,
  C) and, proposed in `docs/deployment/client-owned-vercel-supabase.md`, as a client-owned cloud account (Mode D). Each mode has a
  different install, backup, identity, upgrade and support cost. One person with agent assistance cannot support all of them. Which
  does Verity commit to, and which does it explicitly not?
* **Context** (read 2026-10-22):
  * Hosted multi-tenant is the shape the platform was built and tested for, and the shape every current demo client uses.
  * D & S Electric Works, the one live client, wants its data on its own premises on a Windows Server 2019 host. A Mode B package
    exists and was rehearsed end to end on a Linux stack (Task 129 B1 to B5: Keycloak, TLS proxy, bundled object store, a
    destroy-and-restore of the whole recovery set, and no outbound route by network construction). It has not run on DSEW's hardware.
  * Mode C (no internet at install or at runtime) would also need an offline image and dependency path, vendored fonts and an
    internal registry. No client requires it.
  * Mode D (the client's own Vercel and Supabase accounts) had seven open blockers in the research note, among them that
    `verity_app` is created by no migration and that the HQ operator model assumes one shared database.
* **Decision**:
  1. **Hosted multi-tenant is the default and the only mode offered to a new client** unless that client has a stated reason to
     need its data on its own premises.
  2. **Mode B (private network) is supported for exactly one client, D & S Electric Works,** as a validation target. "Supported"
     means the package, the runbook and the rehearsal evidence exist; it does not mean validated. The word "validated on Mode B for
     D&S" is used only after the Task 129 B7 gate passes on hardware matching DSEW's survey.
  3. **Mode A** remains what the base compose package is (the application, PostgreSQL and the scheduler with external identity and
     storage). It is a component of Mode B, not a separately sold mode.
  4. **Modes C and D are parked.** No design work, no build work, no capacity or install claim, and no proposal, statement of work
     or demo wording that promises either, until a named paying client requires it and the product owner reopens this decision.
  5. **A second on-premises client** does not get Mode B automatically. It is a new decision, priced as a project, and starts from
     the validated DSEW result rather than the rehearsal.
  6. **No generative language model runs on an on-premises host.** Mode B ships with AI off and no outbound route. If a client opts
     in to the assistant, the existing agent channel calls an OpenAI-compatible endpoint through one allow-listed route, per tenant,
     as the caller's own `ActorContext` (ADR-017). The route is added beside the closed network, never by opening it.
     **Exception (amendment 2026-10-24):** a small encoder decision model (Laya, ADR-027 amendment: about 421M parameters, about
     1 GB of memory, no text generation) may run on the host as its own local service, off by default, per tenant opt-in, with no
     outbound route. It answers typed questions for the advisory workflow node (Task 119) and never runs the assistant. It is
     enabled only for a named workflow that needs it, after its threshold is validated on that workflow's labelled data (ADR-027
     calibration caveat) and its CPU latency is measured on the client's host.
* **Constraints**:
  1. ADR-031 constraint 1 stands: any claim names the mode and host it was measured on.
  2. ADR-031 constraint 2 stands: no unproven mode is sold.
  3. This ADR changes no invariant, `enforcePolicy()`, INV-001 or ADR-017.
* **Consequences**:
  * Proposal and demo documents for DSEW describe Mode B as "built and rehearsed, validation on your hardware pending".
  * `docs/deployment/client-owned-vercel-supabase.md` stays as research and is marked parked.
  * Support load is bounded to two shapes: the hosted platform and one on-premises installation.
* **Amendment 2026-10-24** (clause 6): the line was drawn at *generative* models. The reason for the rule (unknown CPU and RAM,
  poor quality of a small generative model, and the no-egress test as the client's trust story) does not apply to a roughly
  1 GB encoder that makes no outbound call. The product owner pointed this out the same day. Nothing is installed or promised:
  DSEW has not asked for AI-decided workflow branches, and the latency on a 4 vCPU / 16 GB host is not measured.
* **Review**: reopen when a paying client requires Mode C or D, when a second client wants on-premises, or when the DSEW validation
  shows Mode B needs more than a small, documented operator effort.
