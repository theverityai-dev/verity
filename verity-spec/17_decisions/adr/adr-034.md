# Architectural Decision Record

## ADR-034: HQ client lifecycle, operational health projection, invite re-issue and support sessions

* **Decision ID**: ADR-034
* **Status**: ACCEPTED and IMPLEMENTED (2026-10-06) under the product owner's delegation to decide open items; item 3 narrowed to visibility (no invitation link exists to resend; see `clients/colonel-kebabz/reference-parity/DECISIONS.md`). Built: migration `20261006020000_hq_client_lifecycle_health`, `setClientStatus`/`enterClient(reason)` in `operator.ts`, fail-closed `listMemberships` and API keys, HQ needs-attention view and support banner.
* **Amends**: ADR-013 (Global HQ Operator Security Model). Does not change INV-001, ADR-017 or
  `enforcePolicy()`.
* **Question**: Four things the HQ audit (`docs/audits/2026-10-05-hq-audit.md`) shows an operator
  needs touch the operator security boundary: knowing which client is unhealthy, giving a client a
  lifecycle (onboarding, active, suspended), re-sending an invitation, and acting inside a client for
  support. How is each done without widening cross-tenant access?
* **Context**: ADR-013 allows exactly three cross-tenant reads (client directory, platform activity,
  platform audit), as fixed `SECURITY DEFINER` projections returning metadata and aggregates, never
  business rows. Everything else is "enter one client, then ordinary tenant-scoped operation". The
  audit found, on the live Colonel Kebabz tenant: 71 undelivered events that HQ never surfaced, an
  owner who is still "Invited", and no way to resend an invite or see platform-wide failures.
  Operators therefore find problems by opening each client's tabs one at a time.

* **Decision (proposed)**:

  **1. Operational health is a column extension of the existing projection, not a fourth projection.**
  `verity.operator_platform_activity` (ADR-013's "platform-wide operational view") gains four integer
  columns per client: `undelivered_events`, `sync_exceptions`, `sla_breached` and `people_invited`
  (memberships still in the Invited state). Counts only, fixed column set, `STABLE`, read-only,
  invocation logged, no dynamic SQL, no business rows: every ADR-013 constraint is unchanged. The HQ
  overview and client directory render these as a "needs attention" list. This is preferred to
  iterating clients through the "enter client" path, which would write an operator-audit entry per
  client on every page load.

  **2. A client has a lifecycle state.** `Tenant.status` is a closed set `onboarding | active |
  suspended`, default `active` for existing rows. HQ shows it in the directory. `suspended` is
  enforced where membership resolves, failing closed: a suspended client's users cannot act, and an
  operator can still enter to inspect. Changing state is an operator command
  (`verity.platform.set_client_status`) with a mandatory reason, audited with the operator marker.
  Suspension never deletes or alters tenant data.

  **3. Re-issuing an invitation reuses the existing path.** `verity.platform.resend_invitation`
  re-sends to an `Invited` membership's recorded, unverified contact through the same notification
  pipeline as `invite_person`; it creates no credential, bypasses no verification (ADR-007) and
  cannot target a membership that is not `Invited`. Password reset is not offered here: it stays with
  the identity provider (ADR-020). Note: no email transport is connected today (notifications are
  in-app only), so resending is only useful once one is, or if the invite is shown to the operator to
  pass on; that dependency is open.

  **4. Support sessions are the existing "enter client" action with a stated reason and a visible
  banner.** Entering a client already writes an operator-marked audit entry. This adds a required
  reason (free text, stored on that entry) and a persistent in-app banner while the operator acts
  inside a client. It adds no new authority: the operator's role and `enforcePolicy()` still decide
  every command (ADR-017).

* **Not decided here**: billing and plans (B-group of the audit), a platform-wide failed-command
  list (needs its own projection decision), operator-team management in the UI (ADR-013 deliberately
  keeps operator bootstrap off the web).
* **Consequences**: one migration (four function columns; one `Tenant.status` column with a CHECK),
  one enforcement point on membership resolution, two new commands, one banner. Tests: isolation test
  that a suspended client's user is refused and an operator is not; projection test that the new
  columns return counts only; invite test that resend cannot target a verified membership.
