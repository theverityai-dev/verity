# Architectural Decision Record

## ADR-039: Outbound notifications go through an outbox, per-tenant opt-in, at-least-once

* **Decision ID**: ADR-039
* **Status**: ACCEPTED (2026-10-09), decided by the engineering lead under the product owner's
  standing instruction to take open decisions from project context (Task 125 item 7.7).
* **Question**: `domain_event.delivered_at` is never set because nothing dispatches events. Clients
  expect reminders and alerts (low stock, a complaint raised, an approval waiting). What is the
  delivery design?
* **Decision**:
  1. **The event table is the outbox.** A dispatcher job (the scheduler of ADR-015) reads undelivered
     `domain_event` rows per tenant, in order, and for each event that a tenant has subscribed to
     builds one notification and sends it. It sets `delivered_at` only after the provider accepts it.
  2. **At-least-once with an idempotency key** (event id plus channel plus recipient), so a retry
     after a crash never sends twice to a provider that honours the key, and a duplicate is at worst
     one repeated message. Failures retry with exponential backoff up to a cap, then the event is
     marked `failed` with the provider's code (no payload) and surfaces in the ADR-036 failure view.
  3. **Per-tenant opt-in, per event type, per channel.** Nothing is sent unless a client
     administrator has turned that event type on for a channel and named recipients. Default off.
  4. **Channels are adapters behind one seam** like storage: in-app first (a tenant-scoped
     notification row the shell lists, no provider needed), then email, then a WhatsApp-class
     provider. The first build is in-app only, because it needs no credential and no external
     account, and proves the dispatcher, retries and opt-in end to end.
  5. **Provider credentials live in the existing encrypted credential registry** (MET-AUT-003), per
     tenant; a message carries only what the recipient may already read (the entity label, never
     figures a role could not see).
* **What this is not**: not a change to INV-001, ADR-017 or `enforcePolicy()`; the dispatcher
  enumerates tenants under ADR-016.
* **Consequences**: a dispatcher in the scheduler, a notification table and a subscription table
  (tenant-scoped, RLS), an adapter seam, and a settings screen. **Built 2026-10-09, in-app channel
  only:** migrations `20261009080000_notification_outbox` (`notification_subscription`, `notification.dedupe_key`
  with a partial unique index, grants for tenant administrators) and `20261009081000_domain_event_delivery_policy`
  (the missing UPDATE policy; the outbox could not drain without it because `domain_event` had only read and
  append policies, and the write-once trigger already limits the change to `delivered_at`). A platform schedule
  (`registerPlatformSchedule`, new, not gated on any capability) runs `dispatchEvents` for each tenant. Default
  off; a subscription covers only events after it is made; the person who caused an event is not alerted; a
  recipient's own opt-out is stored as Suppressed; bodies carry the kind of record, never a figure.
  UI: `/notifications` for every signed-in person (the bell no longer needs Audit access) and Settings > Alerts.
  **Open:** email and WhatsApp-class adapters and the per-tenant credential registry (clause 5); the
  retry-with-backoff and `failed` state, which only matter once a channel can fail (an in-app insert has no
  provider to refuse it); a poison event would stall one tenant's queue, which an external channel must handle.
  Side effect: HQ's "undelivered events" health count (ADR-034) now drains instead of only growing, so it starts
  to mean what its name says.
