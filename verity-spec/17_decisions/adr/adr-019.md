# ADR-019 — Payload CMS rejected as tenant-scoped control-plane dependency

**Date:** 2026-09-08
**Status:** ACCEPTED
**Supersedes:** nothing. Formalizes, at ADR level, the directional verdict
already reached in `taskplans/archive/03_payload_audit.md` and
`taskplans/14_capability_matrix.md`.

## Context

The product owner asked whether Payload CMS should be adopted as Verity's
configuration/control-plane layer — custom fields, dynamic forms,
workflow/approval definitions, document/email templates, module and
navigation configuration — rather than building that layer natively as
planned (`CLAUDE.md` build-priority item 10, "Configuration / capability /
extension infrastructure," still unbuilt).

Payload was already audited in this project's R&D program
(`taskplans/archive/03_payload_audit.md`, against `payloadcms/payload` commit
`72ee175`) and cross-referenced against ten other reference systems
(`taskplans/14_capability_matrix.md`). Those documents already carried
per-feature verdicts (ADOPT/ADAPT/INSPIRE/REJECT/DEFER) but had not been
weighed as a full "Payload as control plane" option against the native
path, with the security/tenancy analysis that decision needs. This gap
is closed in full in `taskplans/103_payload_cms_control_plane_adr.md`,
which this ADR ratifies the settled conclusion of.

## Decision

**Payload CMS (or any comparable second application framework with its
own database-access layer) is rejected as the authoritative control plane
for any tenant-configurable Verity data** — custom fields, workflow/
approval definitions, feature/module configuration, or any other data
whose correct value depends on `tenant_id`.

The reasons, in order of weight (per `103_payload_cms_control_plane_adr.md`
section 15's scoring, tenant isolation weighted 25%, the highest of nine
criteria):

1. **A second tenant-access enforcement surface.** Verity's tenant
   isolation (INV-001) is enforced by Postgres RLS plus `withTenant()`,
   fails closed (no scope set means no data), and is verified by
   `assertRlsEnforceable()`. Payload's own query layer (Drizzle-based) has
   no equivalent — a Payload collection's `access` functions fail **open**
   by default, the opposite failure mode, and would need to be
   hand-verified correct on every collection, forever, as new ones are
   added. This is a structural risk, not an effort/polish gap a later
   design pass could close.
2. **A second authorization decision point.** ADR-017 established that
   every actor, human or AI, executes through the same `ActorContext` and
   the same `enforcePolicy()` gate, with no elevated or parallel path.
   Payload's `access` functions, even fed Verity's session, are a second
   authorization decision *in substance* — the decision logic lives
   outside `enforcePolicy()`. ADR-017 was written to foreclose exactly
   this shape of exception.
3. **Standing multi-tenancy directive.** `taskplans/14_capability_matrix.md`
   already directs multi-tenancy to "logical partition via `tenant_id` +
   RLS" and explicitly rejects Payload's multi-database-adapter model.
   This ADR does not reopen that; it extends the same reasoning to
   Payload's access-control model specifically.

**What is not rejected:** the architectural *patterns* Payload's audit
found valuable — independent of whether Payload itself is ever installed.
Adopt conceptually into Verity's own native design: declarative
schema/configuration-as-data; metadata-driven forms; a reusable local
server API/service abstraction (Payload's `payload.find()`/`payload.create()`
pattern, adapted); field-level authorization as a concept, re-expressed
through `enforcePolicy()` rather than a parallel gate; hooks/lifecycle
concepts, re-expressed through the existing Command pipeline; the
version/draft model as a shadow-table pattern; generated/admin-driven CRUD
patterns. Do not inherit, under any future proposal either: Payload's
database ownership, Drizzle as a second query authority, Payload auth or
access control as an authority, Payload's multi-DB abstraction, or a
second tenant-isolation mechanism of any kind.

A narrower, explicitly bounded option — Payload confined only to content
that is never tenant-scoped (marketing content, platform-global document
templates, SOPs, a read-only industry-template catalog) — remains a
legitimate *future* candidate per `103_payload_cms_control_plane_adr.md`
section 5 (Option C), but is not decided or authorized by this ADR. It
requires its own trigger (a demonstrated velocity bottleneck in the native
admin tooling once built) and its own review at that time.

**What is explicitly not settled by this ADR:** the specific native
implementation shape for item 10 (which tables, which field-type enum,
which condition grammar for workflow/approval rules, which tables need
version history). `taskplans/104_verity_native_configuration_extension_
architecture.md` is the design document for that question; it carries
five open questions of its own and is not yet final. Treating "Payload is
rejected" as equivalent to "therefore this exact native design is right"
would be a second, unrelated claim smuggled in under this one — this ADR
makes only the first claim.

## Consequences

- Item 10 ("Configuration / capability / extension infrastructure") is
  built natively, on the existing platform substrate
  (`src/server/platform/entity.ts`, `capability.ts`, `config.ts`,
  `workflow.ts`, `policy.ts`, `command.ts`, `state.ts`).
  **Correction, same day:** this ADR was drafted assuming item 10 was
  unbuilt, per `CLAUDE.md`'s build-priority list at the time. Checking
  `src/server/platform/` directly (`taskplans/104_verity_native_
  configuration_extension_architecture.md`, corrected 2026-09-08) found
  four of the five configuration pieces this ADR's own analysis sketched
  already shipped — `TenantActivation`, `CustomFieldSchema`, the
  `WorkflowDefinition`/`EdgeCondition` engine, and `contribution.ts`'s
  navigation — just never labeled "item 10." This does not change the
  DECISION above (Payload rejected), which never depended on item 10's
  build status, only on tenant isolation's enforcement mechanism.
- No new external dependency is added to the build for configuration/
  control-plane purposes.
- `03_payload_audit.md` and `14_capability_matrix.md` are not superseded;
  this ADR is the formal record that closes the "should Payload become
  the control plane" question they left implicit.
- Any future proposal to introduce Payload (or a similar framework) for
  the bounded, non-tenant-scoped surface described above must show, per
  table, that no column depends on `tenant_id` — citable against this ADR
  and against `103_payload_cms_control_plane_adr.md` section 7.

## What was rejected

- **Payload as authoritative control plane for tenant-configurable data**
  — rejected per the reasoning above; fails the highest-weighted
  criterion in `103`'s scoring by construction, not by a close call.
- **Full multi-database-adapter architecture** (Payload's own model,
  supporting Postgres/SQLite/MongoDB) — already rejected by
  `14_capability_matrix.md`; restated here as part of the same family of
  decision.
- **Treating this ADR as also settling item 10's implementation shape** —
  explicitly not done; see `104_verity_native_configuration_extension_
  architecture.md` for that still-open design work.
