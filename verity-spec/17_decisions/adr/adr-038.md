# Architectural Decision Record

## ADR-038: Platform announcements are platform-owned content, read by clients, never written into them

* **Decision ID**: ADR-038
* **Status**: ACCEPTED (2026-10-09), decided by the engineering lead under the product owner's
  standing instruction to take open decisions from project context (Task 125 item 7.6).
* **Question**: HQ audit B7 asks to message one, some or all clients and to announce maintenance
  windows. Writing a message into many clients' data would be a cross-tenant write.
* **Decision**:
  1. **One global table, written by operators only.** `platform_announcement` holds the text, the
     audience (all, or a list of tenant ids), a start and an end time, and a severity. It carries no
     tenant data and is not tenant-scoped, like the catalogue tables; the runtime role gets
     `SELECT` only on it and writes happen through one `SECURITY DEFINER` function that requires
     platform operator authority and writes a platform audit row (the Task 124 rule: a global table
     is read-only for the runtime by default).
  2. **Clients read, never receive a copy.** The shell calls one definer function that returns the
     active announcements whose audience includes the caller's tenant. Nothing is inserted into any
     tenant table, so there is no cross-tenant write and nothing for a tenant to delete or edit.
  3. **Dismissal is per person** and stored in the person's own tenant (a small tenant-scoped row
     keyed by announcement id), never in the global table.
  4. A maintenance window is an announcement with a start and an end; it informs, it does not
     block sign-in (suspension, ADR-034, does that).
* **What this is not**: not a change to INV-001, ADR-017 or `enforcePolicy()`.
* **Consequences**: a migration (global table, two definer functions, one tenant-scoped dismissal
  table), an HQ screen, a shell banner. **Build is authorised by this ADR; not built yet.**
