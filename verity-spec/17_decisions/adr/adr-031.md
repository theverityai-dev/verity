# Architectural Decision Record

## ADR-031: Supported deployment modes — Mode A first, B and C not promised

* **Decision ID**: ADR-031
* **Question**: "On-premise" can mean three materially different things: the
  application on the client's server but still using internet services for
  identity and file storage (A); a fully private network with self-hosted
  identity and object storage (B); or no internet at all (C). Which of them does
  Verity promise to support, and which does a first measured reference
  deployment validate? Without an answer, "on-prem" is sold as if it meant C
  while only A has been built and exercised.
* **Context**: Task 123 (enterprise readiness evidence program) is producing
  measured load, restore and install evidence. A measurement is only as honest
  as the deployment it was taken on, so the evidence target must be named
  before Phase 5 builds an install package. What exists today, read 2026-10-01:
  * Containerized runtime and reference `docker-compose.yml` (Task 30/31):
    application plus PostgreSQL 16, runtime role `verity_app`
    (NOSUPERUSER NOBYPASSRLS), migrations as an explicit operator step.
  * Identity: ADR-020 makes a complete OIDC browser relying party the initial
    on-prem identity profile (`VERITY_AUTH_PROVIDER=oidc`). The IdP is external
    to Verity; whether it is internet-hosted or self-hosted on the client's
    network is the operator's choice, but no self-hosted IdP has been
    deployed or tested with Verity.
  * Storage: two bound drivers behind one seam, Supabase Storage
    (`src/server/storage/supabase.ts`) and an S3-compatible driver
    (`src/server/storage/s3.ts`). An S3-compatible store on the client's
    network is therefore architecturally possible; it has not been deployed or
    measured.
  * Scheduler: `POST|GET /api/scheduled` with `CRON_SECRET` (ADR-015/016) and
    `scripts/run-scheduler.mjs` for hosts with no platform cron.
  * Observability: `/api/health`, `/api/ready`, `/api/metrics` (Task 40),
    in-memory and per instance.
  * Not built or proven: a clean-host installer, backup and restore tooling, a
    timed disaster-recovery drill, any measured capacity.
* **Decision** (design; nothing is built by this ADR): three named modes, with
  exactly one promised now.

  | Mode | Shape | Status |
  |---|---|---|
  | **A — internet-connected on-prem** | Verity and PostgreSQL on client infrastructure; OIDC identity and object storage may be external or internet-reachable services | **First supported mode; the target Task 123 validates** |
  | **B — private network** | Verity, PostgreSQL, a self-hosted OIDC IdP and a self-hosted S3-compatible store, all inside the client network, internet not required at runtime | **Not promised.** Candidate second mode; needs its own evidence |
  | **C — air-gapped** | Everything local, no internet at install or runtime, including image and dependency delivery | **Not promised.** Out of scope until a named client requires it |

* **Constraints**:
  1. **Name the mode in every claim.** Any capacity, restore or install result
     produced under Task 123 states which mode it was measured on. A result
     measured on Mode A is never presented as a Mode B or C result.
  2. **No unproven mode is sold.** B and C may be discussed as possible
     directions, but no proposal, SOW or capacity document may promise them
     until a successful install and reproduced run exist for that mode. The
     existence of an S3 driver or an OIDC relying party is an ingredient, not
     evidence.
  3. **Evidence storage is sized separately from the database.** File bytes live
     in object storage, not PostgreSQL (`evidence` rows hold references). A
     database benchmark states that binary evidence objects were not
     generated, and object-storage capacity is stated as its own figure. For a
     Mode A deployment the object store is an external dependency of the
     client's choosing, so its capacity is the client's provisioning
     responsibility, stated in the deployment responsibilities, not silently
     absorbed into a Verity promise.
  4. **Isolation and role rules are unchanged in every mode.** The runtime
     connects as `verity_app`; `assertRlsEnforceable()` refuses a bypassing
     role; tenant context comes from the authenticated context, never a
     payload (INV-001, PLA-TEN-006). No mode may weaken these to ease
     installation.
  5. **No new boundary without its own ADR.** If making B or C work requires a
     new provider binding, a new identity flow, or any surface that can read
     tenant data outside `enforcePolicy()`, that is a separate ADR before code
     (stop conditions, ADR-017, ADR-019).
  6. **Mode A still must be installable by an operator from a package.** "A"
     describes network dependencies, not a lower operational bar: a scripted
     install, scripted migrations, a backup and a rehearsed restore are
     required before it counts as validated.
* **Not decided here**: pricing, SLA wording and support terms; which
  S3-compatible or OIDC product a client runs; when B becomes a commitment;
  whether any real client requires C. Those need product-owner input and, for B
  and C, their own evidence and ADRs.
* **Rejected**: promising "on-prem" without naming a mode (the failure this ADR
  exists to prevent); building B and C speculatively ahead of a client that
  needs them (feature expansion the Task 123 rule forbids until measurement
  exists); treating the presence of the S3 driver as proof Mode B works.
* **Status**: `ACCEPTED` 2026-10-09, decided by the engineering lead under the product owner's
  standing instruction to take open decisions from project context. Basis: Mode A is the only mode
  that has been built and exercised (compose stack, OIDC relying party, two storage drivers, the
  scheduler script), and the target market (10 to 100 person businesses, one shared deployment) has
  no air-gapped or private-network client. Modes B and C stay unpromised until a named client needs
  them and an install plus a reproduced run exist. (Originally `PROPOSED` 2026-10-01, recommending
  Mode A.) Task 123 Phase 5 may build its install package against Mode A.
