# Architectural Decision Record

## ADR-043: Menu prices can differ by outlet and channel, resolved by one rule

* **Decision ID**: ADR-043
* **Status**: PROPOSED (2026-10-09), awaiting product-owner approval. Nothing is built.
* **Question**: A menu item has one price (`menu_item.price_minor`). Restaurants price the same dish
  differently for the Zomato menu than for dine-in, and one outlet may charge more than another. URY
  solves this with a `URY Menu` per branch, per room and per order type, each tied to an ERPNext price
  list. How does Verity express a scoped price without a second pricing concept?
* **Context**:
  * Comparison row "Menu" in `docs/reference/ury-parity/ury-vs-verity-a-to-z.md`. URY evidence:
    `URY Restaurant.room_wise_menu`, `order_type_wise_menu`, `Aggregator Settings.price_list`.
  * Verity already scopes **availability** by outlet, channel and time window
    (`menu_availability`, Task 125 items 3.2 and 3.3) and resolves it in one pure function
    (`src/lib/menu-availability.ts`). Price scoping is the same question with a number attached.
  * Order lines snapshot name and price at the time they are added, so history never moves. Price
    history (item 3.4) reads the audit trail written by `edit_menu_item`.
  * Colonel Kebabz DECISIONS.md #5: HQ sets prices and outlets cannot edit them; a change takes effect
    from a stated date and the old price is kept.
* **Decision**:
  1. **A price rule is a row**: `menu_price_rule` (item, optional outlet, optional channel, price in
     minor units, effective from, effective to). The item's own `price_minor` stays as the base price.
     There are no price lists, no price-list documents and no per-aggregator entities.
  2. **One resolution rule, one function.** For an item, outlet, channel and instant (evaluated in the
     outlet's time zone, using its business day), the matching rules are those whose outlet is the order's
     outlet or null, whose channel is the order's channel or null, and whose window contains the instant.
     The most specific wins: outlet and channel, then outlet only, then channel only, then the base
     price. Ties within a specificity go to the latest `effective from`. The function is pure and lives
     beside the availability rules; the order pad, the self-order surface (ADR-042), the bill and the
     kitchen all call it. Nothing else computes a price.
  3. **Portions and add-ons stay additive.** A portion's delta and an add-on's price apply on top of the
     resolved price. Per-portion rules are not built.
  4. **Authority follows existing scope.** Creating or ending a rule needs `Edit` on the menu item. A
     grant scoped to one outlet can manage that outlet's rules; a tenant-scoped grant can manage tenant-wide
     rules. This uses the permission scopes that exist (PLA-AUT-002) and adds no primitive. Under DECISIONS.md
     #5 only head-office roles are granted tenant-scoped `Edit`.
  5. **Visible, not magic.** The order pad and the Menu screen show which rule produced a price
     ("Zomato price", "Defence Colony price") so a cashier is never surprised (PRN-001). Menu has a
     Prices tab beside Hours, listing rules with their windows; price history includes rule changes.
  6. **Snapshot is unchanged.** The line stores the resolved unit price; a rule edited later never
     rewrites an order already taken.
* **Not decided here**: zone or room pricing (AC vs non-AC), percentage mark-up rules, tax-inclusive
  prices, combos. Triggers are in the taskplan.
* **Constraints**:
  * Money is integer minor units. A rule cannot be negative; a rule equal to the base price is refused as
    pointless.
  * Overlapping rules at the same specificity are allowed and resolved by the tie rule; the Prices tab
    warns when two overlap so the owner sees it.
  * New table is tenant-scoped with forced RLS; rule edits are audited commands.
* **Rejected**:
  * Price lists as documents (ERPNext, URY): a second concept beside item and rule, and the source of
    "which list did this use" disputes.
  * A markup percentage per channel: rounding ambiguity and surprise; revisit if a client asks.
  * Storing channel prices as extra columns on the item: fixed channel set, no dates, no outlet scope.
* **Consequences**: one migration (`menu_price_rule`); the resolver function with tests mirroring the
  availability tests; `listMenu`, `addOrderLines` and the pad call it; Menu gains a Prices tab; the
  platform-payouts match is unaffected (it compares bill totals).
* **Owner**: Product Owner
* **Supersedes**: nothing. Extends Task 125 items 3.2, 3.3 and 3.4 and applies DECISIONS.md #5.
