# Architectural Decision Record

## ADR-029: External tool-invocation surface (machine callers such as Relay)

* **Decision ID**: ADR-029
* **Question**: How may a non-human system (Task 120's Relay, or any later
  integration) call Verity commands and queries over HTTP, without adding a
  second authority path or a second authorization model?
* **Context**: `buildToolManifest()` already produces the actor-scoped tool
  list; nothing accepts an external `{tool, input}` call. `CLAUDE.md`'s stop
  conditions require an ADR before any new externally reachable surface, and
  Task 120 names rate limits, replay protection and which tenants/roles may be
  targeted as the security review it needs first. The product owner authorized
  Task 120 on 2026-09-30 but did not waive that review.
* **Decision**: An external caller is a real, provisioned identity that
  authenticates with a machine credential and then executes as an ordinary
  `ActorContext` through the ordinary pipeline. There is no service account,
  no elevated path and no carve-out in `policy.ts`.
* **Constraints**:
  1. **ADR-017 holds unchanged.** The credential resolves to one User with one
     membership and one Role. `enforcePolicy()` decides every call; channel is
     recorded as `api` on the audit trail and consulted by no rule.
  2. **The credential is not the identity.** A key is a revocable, expiring
     handle to a provisioned User (`provisionIdentity()`, ADR-007). Revoking the
     key ends machine access without touching the identity or its role.
  3. **Keys are high-entropy and hashed at rest.** 32 random bytes, shown once
     at creation, stored only as a SHA-256 hash plus a non-secret lookup id. A
     database dump yields nothing replayable. Comparison is constant-time.
  4. **Tenant comes from the credential, never the request** (PLA-TEN-006).
     The key row fixes the tenant; a payload cannot name another.
  5. **Only tools the actor is already offered.** The dispatcher resolves the
     requested key against `buildToolManifest()` for that actor. An unknown
     tool and a tool the actor holds no grant for return the same error, so the
     surface cannot be used to enumerate the registry.
  6. **No destructive commands externally.** Commands whose manifest `impact` is
     `destructive` are not invocable over this surface. A later ADR may open
     specific ones; the default is closed.
  7. **Commands require an idempotency key**, deduplicated per key identity, so
     a retried webhook cannot apply twice. This, plus TLS, is the replay
     defence; request signing was considered and rejected as a second secret to
     manage for no additional guarantee over a bearer credential on TLS.
  8. **Existing rate limits apply** (`limitActorRequests`, keyed on the acting
     user), so a leaked key is bounded by the same budget as a human session.
  9. **Fails closed and dark by default.** No key store bound means the route
     returns `503`, never an unauthenticated execution (the ADR-015 posture).
  10. **Every call is auditable.** Commands already write `Activity` with
      channel `api`; the key id is recorded on the security stream at creation
      and revocation (`ApiKeyGenerated` exists for this).
* **Not decided here**: the Relay-side contract (Relay has no backend), the
  outbound Verity-to-Relay adapter (needs that contract), and where the
  credential-encryption key lives (still the open platform question).
* **Rejected**: a shared service account with a broad role (violates ADR-017
  and INV-001's least-privilege intent); per-request HMAC signing (above);
  accepting a tenant id in the payload (violates PLA-TEN-006); exposing the
  whole registry and relying on `enforcePolicy()` alone (leaks what exists).
* **Status**: `PROPOSED` — the design is complete enough to build against, but
  an externally reachable authentication surface should be reviewed by the
  product owner before it exists. Nothing in this ADR is live: the primitives in
  `src/server/platform/external-tools.ts` are inert and no route exists.
* **Owner**: Product Owner
* **Supersedes**: nothing. Applies ADR-017 and ADR-007 to machine callers.
* **Implementation so far**: `external-tools.ts` (key mint/verify, manifest-
  scoped dispatcher) with pure tests. **Still to build, in order:** an
  `ExternalApiKey` table with RLS and a `SECURITY DEFINER` lookup function (the
  tenant is unknown until the key is read, so an ordinary RLS read cannot find
  it), the idempotency store, then `POST /api/tools/invoke`. Each needs a real
  database to test, which is why they are not built blind.
