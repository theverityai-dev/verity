# Architectural Decision Record

## ADR-044: Business documents post to the ledger through events, idempotently, by a per-tenant account map

* **Decision ID**: ADR-044
* **Status**: PROPOSED (2026-10-16). Not accepted: it adds a cross-capability write path, so it needs the
  product owner's decision before any posting code is written (`CLAUDE.md` stop conditions). The read-only
  statements (profit and loss, balance sheet) built under it do not depend on acceptance.
* **Question**: Invoices, payments and credit notes in `trading`, and recorded invoices and receipts in
  `project`, never reach the `accounting` ledger, which only takes manual journal entries. Both references
  (Odoo `account`, Manager) make posting the core of accounting. How do documents post to the ledger without
  coupling capabilities, double-posting, or guessing accounts?
* **Context** (read 2026-10-16, see `clients/dsew/reference-parity/accounting.md`): the ledger is
  append-only with reversal (`JournalEntry.reversalOfId`); documents are written by commands that emit
  events; ADR-039 already built an outbox over `domain_event` with a dispatcher in the scheduler,
  at-least-once delivery and an idempotency key; ADR-017 fixes one authorization path; ADR-016 lets the
  scheduler enumerate tenants. D & S Electric Works needs Invoice, Payment, Job margin in one ledger
  (`clients/dsew/prd.md`).
* **Decision**:
  1. **Direction.** `accounting` depends on `trading` and `project`, never the reverse. A client without
     the accounting capability is unaffected; a document command never imports accounting.
  2. **Mechanism.** The accounting capability reacts to document events (`invoice raised`, `payment
     recorded`, `note raised`, `document voided`, and the `project` equivalents) and posts one balanced
     journal entry per document. Posting is a Command run as the tenant's accounting service path under
     the same `enforcePolicy()` gate (ADR-017): no elevated or agent-specific authority.
  3. **Idempotency.** Each posted entry carries the source document id and kind as a unique key per
     tenant. Posting the same document twice is a no-op that returns the existing entry. This makes the
     at-least-once outbox (ADR-039) safe and makes the backfill rerunnable.
  4. **Account map, never a guess.** A per-tenant table maps a document line kind to accounts
     (receivable, payable, sales income, purchases or cost of goods, GST output, GST input, cash, bank).
     If a needed mapping is missing the posting is **refused and recorded as pending**, visible on the
     accounting setup screen and the ADR-036 failure view. Nothing is posted to a default account.
  5. **No in-place change.** A voided or credited document posts a reversing entry through the existing
     reversal rule; a posted entry is never edited or deleted (INV-002 spirit, ADR-009).
  6. **Amounts come from the document.** The posting copies the document's own figures (taxable value,
     GST, total). It never recomputes tax, so the ledger cannot disagree with the invoice the customer holds.
  7. **Period rule.** Posting honours the ledger period lock once it exists; a document dated in a locked
     period posts on the first open date and records that it did.
  8. **Backfill.** One idempotent command posts existing documents for a tenant. For D & S the volume is
     small and the tenant is disposable; for a live client it is run per tenant with a dry-run count first.
* **What this is not**: not a change to INV-001, ADR-017 or `enforcePolicy()`; not a second tenant-access
  path (every read and write is tenant-scoped, RLS applies); not auto-creation of a chart of accounts.
* **Consequences**: a posting handler per document kind, an `account_map` table and an `entry source`
  unique key (tenant-scoped, RLS, migration, conformance entries), a setup screen that shows unmapped kinds,
  and tests: idempotent posting, refusal when unmapped, reversal on void, RLS isolation, and the D & S
  acceptance walk (trial balance moves by exactly the invoice and receipt amounts). Until it is accepted
  and built, the Statements page states plainly that it covers journal entries only.
* **Open for the product owner**: accept or amend this design; whether posting is in the same transaction
  as the document (simplest, couples failure) or through the outbox (decoupled, eventually consistent).
  Recommendation: outbox, because a missing account map must not block a sale being invoiced.
* **Rejected**: posting from inside the document commands (couples capabilities and breaks clients without
  accounting); posting to default accounts when a mapping is missing (a silent wrong ledger); computing
  tax again in accounting (two sources of truth); a database trigger (bypasses `enforcePolicy()` and audit).
* **Related**: ADR-009, ADR-016, ADR-017, ADR-036, ADR-039, INV-001, INV-002,
  `clients/dsew/reference-parity/accounting.md`, `taskplans/72_erpclaw_capability_accounting.md`.
