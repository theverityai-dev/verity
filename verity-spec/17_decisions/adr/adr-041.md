# Architectural Decision Record

## ADR-041: Kitchen stations, courses and tickets; printing starts in the browser

* **Decision ID**: ADR-041
* **Status**: PROPOSED (2026-10-09), awaiting product-owner approval. Nothing is built.
* **Question**: URY routes each item to a production unit (a kitchen or bar station) by item group,
  sequences service by course, produces a numbered kitchen ticket per order change, and prints it on
  that station's printer. Verity has one kitchen queue per outlet, no course, no ticket, and prints only
  the bill from the browser. Which of these does Verity adopt, and how is printing done given that the
  application runs on serverless hosting?
* **Context**:
  * Comparison: `docs/reference/ury-parity/ury-vs-verity-a-to-z.md` (rows Courses, KOT, Kitchen display,
    Printing, Production units). URY evidence: `ury/ury/doctype/ury_production_unit`,
    `ury/ury/api/ury_kot_generate.py`, `ury/ury/api/ury_print.py`.
  * `GOV-SCO-006` excludes "B2C retail storefront web checkouts, retail inventory barcode scanners,
    physical cashier cash drawer registry, and retail store return policies". It does not name receipt
    or ticket printers. `KentsRestaurant.md` §15 deferred KOT printers as a *control path* for v1, which
    is a scope deferral, not an exclusion. This ADR records the reading: **printing a ticket or a bill
    is in scope; cash drawers, scanners and card terminals stay out.**
  * Verity's server runs on Vercel (handoffs README 7.10). A serverless function cannot open a socket to
    a printer on the outlet's LAN, so URY's "network printer through the ERPNext print server" has no
    equivalent here. Anything that prints without a person pressing a button must run on the outlet's
    own device.
  * Today a voided line simply leaves the kitchen board. A cook who has already started the dish is not
    told. URY keeps a red "cancelled" card on the display until the kitchen confirms it.
* **Decision**:
  1. **A station is a view over the outlet's kitchen, not a security boundary.** `kitchen_station`
     (outlet, name, sort order, `isDefault`, active) and `kitchen_station_category` (category to station,
     one station per category per outlet). A line is routed at the time it is added and **snapshots**
     `stationId`, so re-mapping a category never moves a line already cooking. A category with no mapping
     goes to the outlet's default station. The kitchen board takes `?station=` and shows that station's
     lines; with no filter it shows all. Permissions do not change: access is by outlet, as today.
  2. **Course is a menu attribute that orders the pass.** `menu_course` (tenant: name, priority) and
     `menu_item.course_id` (nullable). A line snapshots course name and priority. The board sorts by
     course priority within each state and shows the course on the card. Holding and firing a course on
     demand is **not** built (trigger: a client with a tasting-menu service).
  3. **A ticket is a stored fact, not a document users edit.** `kitchen_ticket` (outlet, station, order,
     number, kind `new | addition | void`, created by, created at) and `kitchen_ticket_line` (ticket to
     order line). One ticket is written per station per command that changes what the kitchen must do:
     `place_order`, `add_order_lines`, and `void_order_line` on a line that had already been sent.
     Ticket numbers are per outlet per service day and gapless, using the allocator extracted by
     ADR-040 with the service day in place of the financial year, so numbers restart each morning as URY's
     do. Tickets are append-only.
  4. **A void after fire needs a kitchen acknowledgement.** A line voided while `preparing` or `ready`
     appears on its station as a red "Cancelled, confirm" card until a kitchen user acknowledges it
     (`kitchen_ack_at` on the line). A line voided while still `queued` just leaves. This replaces URY's
     "confirm cancel" button with the same intent.
  5. **Printing is browser printing first.** `/kitchen/ticket/[ticketId]` renders an 80 mm ticket with
     print styles (solid, no materials). A station screen has an "auto print new tickets" mode that opens
     each new ticket for print; for a dedicated station device the supported setup is the browser's
     silent-print launch option, documented in the onboarding checklist. A person can always print or
     reprint by hand. `reprint_ticket` is an audited command that increments a reprint count and stamps
     the paper "REPRINT". Bill printing is unchanged.
  6. **A print agent is deliberately not decided here.** A small program on the outlet's machine that
     polls Verity over HTTPS and drives a thermal printer would need a device credential and a ticket
     feed. That is a new externally reachable surface and gets its own ADR, modelled on ADR-029's machine
     credential, if and when a client cannot use silent browser printing.
  7. **Alerts stay on the device.** New-ticket sound and order-channel colouring are display behaviour
     on the station screen; the on/off choice is a per-device preference, not tenant data.
* **Constraints**:
  * No tenant data is reachable without a signed-in user; tickets are read through ordinary queries
    under `enforcePolicy()` (ADR-017). No new public route.
  * Existing kitchen states, the prep-time clock and the 10-second refresh are unchanged.
  * New entities are tenant-scoped with forced RLS; `kitchen_ticket` and `kitchen_ticket_line` are added
    to the conformance test's append-only list.
  * A line created before this ADR is built has no station; it shows on the default station.
* **Rejected**:
  * Station as a permission scope: a cook seeing only their station is a convenience, not a
    confidentiality need, and role-by-station multiplies roles.
  * Tickets as an editable document with its own workflow (URY's submitted KOT): the kitchen acts on
    lines; the ticket only records what was asked and when.
  * Server-side network printing: impossible from serverless hosting, as above.
  * Building the print agent now: no client has been shown to need it; browser printing covers the
    stated cases.
* **Consequences**: one migration (four tables, columns on `menu_item`, `order_line`); Menu gains
  Courses and Stations setup; kitchen board gains station filter, course badge, cancelled-confirm lane,
  sound, ticket link; floor order pad unchanged. The `GOV-SCO-006` text is **not edited**; this ADR
  records the reading and the taskplan cites it.
* **Owner**: Product Owner
* **Supersedes**: nothing. Narrows `KentsRestaurant.md` §15 (KOT printers). Depends on ADR-040 for the
  extracted number allocator.
