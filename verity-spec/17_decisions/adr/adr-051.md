# Architectural Decision Record

## ADR-051: Record objects and saved views are a platform primitive

* **Decision ID**: ADR-051
* **Status**: PROPOSED (2026-10-20). Written for Task 128 (CRM capability) on the product owner's instruction the same day. Built on
  the local development database only; not accepted until the owner reviews it.
* **Question**: Task 128 stage 2 needs Twenty-style lists: a record table and a board over the same records, with saved views
  (columns, filters, sorts, grouping, a default view, personal or shared). Does that live inside the CRM capability or in the
  platform?
* **Context**:
  * Every capability with a list (jobs, orders, documents, products, people) wants the same thing. Building it inside `relationship`
    would force the next capability to copy it, against the standing rule to place things at the right level from day one.
  * Twenty solves this with a metadata engine that turns every object into dynamic schema. Verity already has typed Prisma models,
    a command/query runtime, RLS and `enforcePolicy()`; ADR-019 rejected a second data-access layer for tenant-configurable data.
  * `CLAUDE.md` treats a new platform primitive as a stop condition; this ADR is that decision, made explicitly.
* **Decision**:
  1. **Record object descriptors (code, not data).** A capability describes a list-able object once in TypeScript: key, labels,
     the entity key it is authorized by, the query that lists it and the fields (key, label, type, which filters and sorts apply,
     which aggregates make sense, and the command that edits it). Descriptors are registered at startup like commands and queries;
     nothing about them is stored in the database.
  2. **Saved views (data).** One platform table, `saved_view`: tenant, object key, name, type (`table` | `board`), a `config`
     document (visible columns with order and width, filters, sorts, group-by field, board aggregate), visibility (`personal` |
     `shared`), owner user, default flag, position, version. Forced RLS. `config` is validated against the descriptor on every save,
     so a view can only name fields the object really has.
  3. **Reads stay in the owning capability.** The view layer never queries a capability's tables. It hands the view's filters,
     sorts and paging to the descriptor's list query, which runs under the caller's tenant and authority like any other query.
  4. **Writes stay commands.** An inline edit or a board drag runs the field's edit command through the ordinary pipeline. The view
     layer adds no write path.
  5. **Authority.** Saving a personal view needs `Create` on `verity.platform.saved_view`; saving, renaming or deleting a shared
     view, or making one the default for everyone, needs `Edit`. Existing roles receive `Read` and `Create`; roles that can edit
     roles also receive `Edit`. Reading a view never grants reading the records it lists: the list query checks that separately.
* **Consequences**:
  * One more platform module (`views.ts`) and one more platform table; the platform-size tripwire in `conformance.test.ts` moves from
    57 to 58 with this ADR as its reason.
  * Custom objects (Task 128 stage 3) are not implied: a descriptor still needs a real model and query.
* **Alternatives rejected**: views inside the CRM capability (copied by the next capability); a Twenty-style metadata engine (a
  second runtime, ADR-019); per-user browser storage (lost between devices, never shared).
