# Architectural Decision Record

## ADR-049: A membership can be disabled; a disabled membership authorizes nothing from the next check

* **Decision ID**: ADR-049
* **Status**: ACCEPTED (2026-10-22). Direction approved by the product owner 2026-10-19 with safeguards; two reviews done
  (2026-10-18 and 2026-10-19, text amended); implementation and tests existed from 2026-10-19 (migration
  `20261019100000_membership_disable`, two commands, `src/test/membership-disable.test.ts`), and on 2026-10-22 the commands gained a
  screen (HQ People: Disable access / Restore access, a sheet that requires a reason), which closes the gap that made offboarding
  an engineer-only step. Accepted under the owner's standing instruction to decide open items from the evidence and record the
  basis; the owner can reopen it. The guarantee is unchanged: "revoked at the next authorization check", not termination of
  in-flight requests. Deployed to production only when the migration is applied there (Task 129 A2 / FINISHER P0b-3).
* **Question**: Disabling a person in the identity provider does not end Verity's already-issued application session (signed
  cookie, 1 h idle, 8 h absolute). How does Verity end a person's access to one workspace promptly, reversibly and with an audit
  trail, without calling the IdP on every request and without weakening RLS, `withTenant()` or authorization?
* **Context** (read 2026-10-18/19, corrected 2026-10-19):
  * `resolveActor()` calls `verity.memberships_for_auth_user(auth_user_id)` on **every** request (`src/server/platform/auth.ts`),
    so access is already decided from Verity's own database each time; the cookie proves identity, the database decides belonging.
  * **A Verity-side revocation already exists and is tested**: `verity.platform.revoke_membership` (`administration.ts`, covered in
    `hq-administration.test.ts`) deletes the membership, so the next request resolves to no actor. It is **irreversible**: it drops
    the role assignment and the organization placement, and the person must be re-invited and re-roled from scratch. An earlier
    draft of this ADR and of `onprem-stage2-design.md` said there was "no verified Verity-side revocation today"; that was wrong
    and is corrected here. What was missing was a **reversible** way to suspend access, not any way to end it.
  * The function is `SECURITY DEFINER`, fixed `search_path`, no PUBLIC execute (CI proves this).
  * Other definer functions also read `tenant_membership`: `authenticate_api_key`, `is_platform_operator`,
    `operator_client_directory`, `operator_platform_activity`, `operator_platform_audit`, `provision_identity`, `party_visible`,
    `user_visible`. Application code reads memberships in `administration.ts`, `operator.ts`, `notification-outbox.ts`, the
    dine-in self-order service, `people.ts`, `access-request.ts` and several capabilities.
* **Decision** (as implemented):
  1. `tenant_membership.disabled_at timestamp(3) NULL`. Scope is **one user in one tenant** (one membership row); a person's
     other memberships are unaffected.
  2. `memberships_for_auth_user` omits memberships where `disabled_at IS NOT NULL`. `SECURITY DEFINER`, fixed `search_path` and
     the PUBLIC revoke are re-applied in the same migration.
  3. The same exclusion where a membership grants authority:
     * `authenticate_api_key` returns no row, so a disabled member's API keys stop working (and `createApiKey` refuses to mint one);
     * `is_platform_operator` is false, so a disabled operator loses HQ, and the three `operator_*` functions that call it return
       nothing;
     * `enterClient` and `operatorActorFor` (which locate an operator's membership inside a client directly) throw rather than
       use a disabled one, and never re-enable it;
     * notification recipient selection skips disabled members.
  4. **Reviewed and deliberately unchanged**: `party_visible` and `user_visible` answer "may this tenant scope see this
     identity row?" and grant no authority. They must keep listing a disabled person so an administrator can see and restore
     them. They fail closed because they are keyed on `current_tenant_id()`, which is only ever set for an actor that passed the
     checks above. The test `party_visible and user_visible keep a disabled person listed in their own tenant, invisible elsewhere
     and with no scope` demonstrates this: visible in the person's tenant, invisible from another tenant's scope, invisible with no
     scope. `operator_platform_audit.is_operator` is historical attribution and must not rewrite history;
     `operator_client_directory.member_count` and `people_invited` count people, not authority; `provision_identity` creates
     enabled rows.
  5. Two commands through `executeCommand` and `enforcePolicy()`, no elevated path: `verity.platform.disable_membership` and
     `verity.platform.restore_membership`. Verb `ActionExecute` on a **dedicated entity** `verity.platform.membership_access`
     (listed in `PLATFORM_ADMIN_ENTITIES` so roles can be granted it, and in `OPERATOR_GRANTS`). `Edit` on `membership` is not
     enough. A **reason of at least 3 characters** is required by the input schema.
  6. **Audit that cannot be erased.** Each command, in the same transaction as the state change, appends to `activity` (access
     Enabled/Disabled plus the reason, actor, tenant, entity id, timestamp, correlation id) and to the security stream with the new
     event types `MembershipDisabled` / `MembershipRestored` (payload: membership, target user, reason), and emits a domain event.
     Restore sets `disabled_at` to null and does **not** delete or edit the disable records; history reads disable, restore,
     disable. `activity` refuses UPDATE and DELETE for the application role.
  7. Guards: no self-disable; the **last active owner** cannot be disabled; a repeated disable or restore is a no-op that writes
     nothing; restore must pass the grant ceiling (an actor cannot restore someone holding more than they could grant).
     * "Owner" means an active membership whose role holds `ActionExecute` on `membership_access` at Tenant scope, **excluding**
       the platform's `Verity Operator` role, so a client can never be left with only HQ support access.
     * A client **cannot disable an operator's support membership** from inside (ADR-035: it is the platform's to withdraw, by
       disabling the operator's platform membership or suspending the client under ADR-034). **Decision flagged for review.**
  8. **Concurrency.** Each command takes a per-tenant `pg_advisory_xact_lock` first. The last-owner count is read after the lock
     under READ COMMITTED, so two owners disabling each other at the same instant cannot both succeed. Tested: 10 rounds, exactly
     one wins and one owner always remains.
  9. **The guarantee, exactly.** Access is revoked **at the next authorization check**. A request already executing may finish.
     The person's signed cookie is not erased and still identifies them; it resolves to no actor in this workspace (a cookie that
     names the disabled membership is not honoured). A person with other active memberships keeps those. This is **not** a claim of
     instant termination of in-flight work.
  10. **No stale cache.** Membership and role are not cached across requests: `resolveActor` re-reads them every request and the
      cookie carries no role. No process-level cache of memberships was found.
* **Evidence** (local database only; commands and results are in the review report):
  * clean schema: all 142 migrations apply; a representative previously migrated database (141 applied) takes the new one;
  * `src/test/membership-disable.test.ts`: 21 tests covering a disabled membership resolving to no actor through the shared
    `requireActor` gate, restore re-enabling, three disable/restore cycles, a cookie naming the disabled membership,
    a two-workspace person keeping the other workspace, API key refused and revived, HQ operator and `operator_*` refused and
    revived, `operatorActorFor`/`enterClient` failing closed, missing/blank/short reasons, insufficient permission (including
    Edit-only), self-disable, last-owner protection, the race, cross-tenant refusal, the grant ceiling, audit rows and
    append-only history, and atomicity (an injected audit-write failure leaves the membership enabled and no activity row);
  * the definer-function ACL, fixed `search_path` and `FORCE ROW LEVEL SECURITY` on `tenant_membership` are asserted in the same file.
* **Not covered / not done**: no People-screen button (the commands are reachable through the command registry; UI is a separate
  piece of work); a real browser session cookie was not exercised end to end (the session path is tested through `resolveActor`
  with a mocked identity provider); no production or DSEW database was involved.
* **Alternatives considered**
  * A session registry or per-user session version: a second source of truth and an extra read or write per request, when a
    per-request membership lookup already exists. Rejected.
  * Calling the IdP on each request to check the account: makes every request depend on Keycloak and defeats the degraded-mode
    contract. Rejected.
  * Deleting the membership (`revoke_membership`, existing): ends access but is irreversible and discards the role assignment.
    It stays for permanent removal; it is the wrong tool for a leave of absence or an incident that may be reversed.
  * Clearing the role as the offboarding method: a null role denies every permission check but leaves a signed-in empty shell and
    is not audited as a revocation. **Not an operating procedure.**
* **Consequences**: one additive migration (column, three redefined functions with re-applied ACLs, two security event types), two
  commands and one new permission entity. Rollback: restore the previous function bodies and drop the column; only the
  `disabled_at` values are lost, the activity history remains. The two enum values cannot be removed from PostgreSQL once added,
  which is harmless (nothing else uses them).
* **Migration impact**: additive and nullable, no backfill; every existing membership stays enabled. The function redefinitions
  change authorization behaviour only for rows that have `disabled_at` set. Per project rules: dry-run on a disposable copy,
  backup first, never `db push` against production.
* **Offboarding with this ADR** (once accepted and deployed): disable the Keycloak account (stops new sign-ins) **and** disable
  the membership in Verity (ends the existing session at its next request, reversibly). Use `revoke_membership` only for permanent
  removal. Until it is deployed on a given environment, only `revoke_membership` ends access there.
* **What this is not**: not a change to INV-001, ADR-017 or `enforcePolicy()`; not a Keycloak administration adapter; not a
  claim of immediate revocation.
