# Architectural Decision Record

## ADR-049: A membership can be disabled; a disabled membership authorizes nothing from the next check

* **Decision ID**: ADR-049
* **Status**: PROPOSED (2026-10-19). Direction approved by the product owner the same day (`disabled_at` on the membership,
  exclusion in `memberships_for_auth_user`, separate audited disable and restore commands), subject to the safeguards below.
  Not accepted until this text is reviewed; no migration or code exists.
* **Question**: Disabling a person in the identity provider does not end Verity's already-issued application session (signed
  cookie, 1 h idle, 8 h absolute). How does Verity end a person's access to one workspace promptly, without calling the IdP on
  every request and without weakening RLS, `withTenant()` or authorization?
* **Context** (read 2026-10-18/19):
  * `resolveActor()` calls `verity.memberships_for_auth_user(auth_user_id)` on **every** request (`src/server/platform/auth.ts`),
    so access is already decided from Verity's own database each time; the cookie proves identity, the database decides belonging.
  * The function is `SECURITY DEFINER`, fixed `search_path`, no PUBLIC execute (CI proves this). Nothing marks a membership as
    disabled today. A null `roleId` denies every permission check (`authorization.ts`), but that is not a revocation mechanism.
  * Other definer functions also read `tenant_membership`: `authenticate_api_key`, `is_platform_operator`,
    `operator_client_directory`, `operator_platform_activity`, `operator_platform_audit`, `provision_identity`, `party_visible`,
    `user_visible`. Application code reads memberships in `administration.ts`, `operator.ts`, `notification-outbox.ts`, the
    dine-in self-order service, `people.ts`, `access-request.ts` and several capabilities.
* **Decision**:
  1. Add `disabled_at timestamptz NULL` to `tenant_membership`. Scope is one **user-in-one-tenant membership**; a person's other
     memberships are unaffected.
  2. Redefine `memberships_for_auth_user` to omit memberships where `disabled_at IS NOT NULL`, preserving `SECURITY DEFINER`,
     fixed `search_path` and the PUBLIC revoke (re-applied in the same migration).
  3. The same exclusion applies wherever a membership grants authority: `authenticate_api_key` (a disabled member's API keys stop
     working), `is_platform_operator` and the three `operator_*` functions (a disabled operator loses HQ). `provision_identity`
     must not silently re-enable. `party_visible` and `user_visible` stay as they are (they govern directory visibility, not
     authority); this is reviewed in the migration PR, not assumed.
  4. Two commands: `verity.platform.disable_membership` and `verity.platform.restore_membership`, verb `ActionExecute`, each
     needing a **dedicated permission** and a **reason (3+ characters)**. They are ordinary commands through `executeCommand`
     and `enforcePolicy()`; no elevated path.
  5. **Audit that cannot be erased.** Each command records actor, target membership, timestamp and reason in the activity record
     and emits a domain event. Restoring sets `disabled_at` to null but does **not** delete or edit the disable record, so the
     history shows disable, restore, disable again. (A column holds only current state; the history lives in `activity`, which
     refuses UPDATE and DELETE for the application role.)
  6. Guards: a person cannot disable their own membership; the last active owner-level membership of a tenant cannot be
     disabled (a tenant must not lock itself out); disabling an already disabled membership is a no-op that returns its state.
  7. **The guarantee, exactly.** Access is revoked **at the next authorization check**. A request already executing may finish.
     The person's signed cookie is not erased and still identifies them; it resolves to no actor in this workspace. A person with
     other active memberships keeps those. This is **not** a claim of instant termination of in-flight work.
  8. **No stale cache.** Role and membership are not cached across requests: `resolveActor` re-reads them each request and the
     session cookie carries no role. The implementation PR must show this by test, and must flag any process-level cache it finds.
* **Required tests** (all before claiming revocation works):
  * a disabled membership resolves to no actor; a server action and an API route both refuse it; restoring re-enables on the
    next request;
  * a person with two memberships keeps the other tenant after one is disabled, and the disabled tenant's data stays unreadable
    even when the cookie names that membership as active;
  * an API key of a disabled member is refused; a disabled operator is refused HQ;
  * self-disable and last-owner disable are refused; the permission and the reason are required;
  * audit rows exist for disable, restore and a second disable, and a restore does not alter the first;
  * negative cross-tenant: an administrator of tenant A cannot disable a membership in tenant B;
  * the definer-function ACL proof (no PUBLIC execute, fixed `search_path`) still passes.
* **Alternatives considered**
  * A session registry or per-user session version: a second source of truth and an extra read or write per request, when a
    per-request membership lookup already exists. Rejected.
  * Calling the IdP on each request to check the account: makes every request depend on Keycloak and defeats the degraded-mode
    contract. Rejected.
  * Deleting the membership: loses history and breaks foreign keys; the platform records closure rather than deleting. Rejected.
  * Clearing the role as the offboarding method: not a revocation mechanism, untested end to end, and leaves a signed-in shell.
    **Not to be documented as an operating procedure** until verified.
* **Consequences**: one additive migration (column, redefined functions with re-applied ACLs, new permission entities), two
  commands, an administration screen action, and the tests above. Rollback: restore the previous function bodies and drop the
  column; only the `disabled_at` values are lost, and the activity history remains.
* **Migration impact**: additive and nullable, so no backfill; all existing memberships stay enabled. The function redefinitions
  change authorization behaviour only for rows that have `disabled_at` set. Per project rules: dry-run on a disposable database
  copy, backup first, never a production `db push`.
* **Offboarding until built**: disabling the Keycloak account stops new sign-ins only. It does not end the existing Verity
  session. There is **no verified Verity-side revocation today**, so the interim runbook must not claim one. The only bounded
  exposure is the 1 h idle and 8 h absolute session limits.
* **What this is not**: not a change to INV-001, ADR-017 or `enforcePolicy()`; not a Keycloak administration adapter; not a
  claim of immediate revocation.
