# Architectural Decision Record

## ADR-030: Public verification passport (an unauthenticated, read-only surface)

* **Decision ID**: ADR-030
* **Question**: Carxen's quotation promises a QR-based product verification
  passport with a public page, so a customer scanning a code on a finished
  seat cover can see it passed inspection. Verity has no unauthenticated
  surface that reads tenant data. How may one exist without weakening INV-001
  or leaking anything a tenant did not choose to publish?
* **Context**: VEDA ships this as `/verify/[id]`. Verity now records the facts
  a passport shows: stage completion times and append-only QC findings
  (Task 118). The hard part is not the page but the boundary: it is a route any
  person on the internet can call, whose data lives behind row-level security
  with no tenant context. ADR-029 solved the analogous problem for machine
  callers with a narrow `SECURITY DEFINER` lookup; the same shape applies.
* **Decision** (design; nothing is built by this ADR): a passport is a
  deliberately **published, revocable, minimal projection** of one completed
  order, reachable only by an unguessable token.
* **Constraints**:
  1. **Published on purpose, never implicit.** A passport exists only after
     an authorized `issue_passport` command runs against an order that is
     `completed` with every QC checkpoint currently passing. No order is public
     by default; completing an order does not publish it.
  2. **Unguessable, not enumerable.** The token is 32 random bytes
     (base64url), shown once in the QR URL and stored only as a SHA-256 hash.
     There is no sequential id, no order id in the URL, and no listing. A
     wrong token and a revoked token answer identically.
  3. **A minimal, frozen projection.** The public page shows: the tenant's
     display name, the product name, an order reference the tenant chose to
     publish, completion date, and per-checkpoint pass/fail for the QC stage
     with label only. It never shows remarks, photos, staff identities,
     customer data, costs, stock, or any other tenant record. The projection is
     computed and stored at issue time (`passport.snapshot`), so later edits or
     rework cannot silently change what a printed code says; a rework or
     recall is a **revocation plus a new issue**, not an edit.
  4. **Lookup is one SECURITY DEFINER function** taking the token hash and
     returning only the snapshot JSON. Row-level security stays fully in force
     everywhere else; the unauthenticated route gets no database role with wider
     reach, no tenant context, and no ability to read any other table.
  5. **Read-only and rate-limited.** GET only, no cookies, no state changes.
     Requests are throttled by source through the shared limiter; the response
     carries `Cache-Control` short enough that a revocation takes effect quickly
     and `X-Robots-Tag: noindex` so it is never search-indexed.
  6. **Photos are opt-in and separate.** Publishing an inspection photograph is a
     different disclosure than publishing a verdict. Not part of this decision;
     a future ADR may allow specific, signed, expiring image URLs.
  7. **Issue and revoke are audited commands** on the ordinary pipeline
     (`enforcePolicy()`, ADR-017), recorded on the security stream; a passport
     holds a tenant-scoped row like everything else.
* **Not decided here**: the QR/label printing format, whether a passport
  may carry the customer's name (default: no), and how long a passport lives.
* **Rejected**: an order-id or sequential URL (enumerable, and leaks volume);
  computing the page live from current data (a rework would silently rewrite a
  printed claim); a public read role with broader table access (a second
  tenant-access surface with no RLS-equivalent, the failure ADR-019 rejected).
* **Status**: `PROPOSED` (2026-09-30), awaiting the product owner's review. It is
  an externally reachable unauthenticated surface, so it needs approval before
  any code, as ADR-029 did.
* **Owner**: Product Owner
* **Supersedes**: nothing. Applies ADR-029's pattern to a public read surface.
* **Implementation when accepted**: `ManufacturingPassport` table (tenant-scoped,
  RLS, `tokenHash`, `snapshot`, `revokedAt`); `issue_passport` / `revoke_passport`
  commands; `verity.passport_lookup(token_hash)` definer function; a public
  route `/verify/[token]`; tests against the real database (wrong/revoked token
  identical, snapshot frozen across rework, no other data reachable, rate limit).
