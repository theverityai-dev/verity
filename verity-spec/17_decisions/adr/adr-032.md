# Architectural Decision Record

## ADR-032: The public origin is configured, never derived from the request

* **Decision ID**: ADR-032
* **Question**: When Verity must send a browser to one of its own pages (after
  sign-in, after a failed sign-in, when sign-in is not configured), which origin
  does it use, and where does that origin come from?
* **Context**: Found 2026-10-02 during the fresh-install verification of the
  bundled object store (finding F6). After a successful OIDC login the callback
  redirected the browser to `http://0.0.0.0:3000/`. Read that day:
  * `src/app/api/auth/oidc/callback/route.ts` built its redirects with
    `new URL(path, request.url)`, and so did `start/route.ts` (sign-in not
    configured) and `logout/route.ts` (no end-session endpoint).
  * In the container image `request.url` takes its origin from the server's own
    bind address: the `Dockerfile` sets `HOSTNAME=0.0.0.0` and `PORT=3000`, and
    the application has no setting for the address a browser actually uses.
  * It had appeared to work only because the published port happened to be 3000
    and the client ran on the same machine. Behind the documented TLS reverse
    proxy, or on any other published port, the browser would be sent to a
    private bind address.
  * `VERITY_OIDC_REDIRECT_URI` already names the public callback explicitly, so
    the application already knows its public origin in an OIDC deployment; the
    redirects simply did not use it. `logout/route.ts` already takes its
    post-logout address from that setting.
  The tempting repair is to trust `Host`, `X-Forwarded-Host` or
  `X-Forwarded-Proto`. Those are attacker-controllable request headers unless a
  proxy is known to overwrite them, and a redirect built from them in an
  authentication callback is an origin-confusion and host-header-injection hole.
* **Decision**: the application has one configured public origin,
  `VERITY_PUBLIC_URL`, and every absolute URL it sends to a browser is built from
  it and nothing else.
  * **Shape.** An absolute `http://` or `https://` origin. It is normalised to
    the origin: the host is lower-cased, a default port and any trailing slash are
    dropped (`https://Example.com/` becomes `https://example.com`). A path other
    than `/`, a query, a fragment or credentials are rejected, so the value cannot
    smuggle anything into the URLs built from it.
  * **Required** whenever the OIDC provider is selected and the application runs
    with `NODE_ENV=production`. A deployment that has a public origin must name it.
  * **HTTPS in production.** When the deployment environment is `production`
    (`VERITY_ENVIRONMENT`, whose default is production) the value must be
    `https://`. A `staging` deployment may use `http://`, exactly as the
    installer's preflight already allows for the identity provider.
  * **Consistency.** When `VERITY_OIDC_REDIRECT_URI` is also set it must be on the
    same origin, so the origin the browser is sent to and the origin the identity
    provider is told to return to cannot disagree.
  * **Development.** Outside production the value is optional and the origin is
    `http://localhost:<PORT>` (3000 by default): an explicit, documented constant,
    still not read from the request.
  * **One helper.** `src/server/platform/public-url.ts` builds the URL: a path that
    does not start with a single `/`, or that would leave the configured origin,
    is refused.
  * **`HOSTNAME` is a bind address.** `0.0.0.0` stays the container's internal
    listen address and is never a browser-facing URL.
  * **Invalid configuration fails clearly**, at the configuration boundary and in
    the installer's preflight, with the variable named.
* **Constraints**:
  1. No code path in authentication may derive an origin from `Host`,
     `X-Forwarded-Host`, `X-Forwarded-Proto`, `Forwarded` or similar. A test fails
     if any appears in `src/app/api/auth` or the platform's auth modules.
  2. No authentication route may build a redirect from `request.url`. A test fails
     if one does.
  3. `returnTo` remains a local path (`safeReturnPath`); it is joined to the
     configured origin and never replaces it.
  4. Nothing here changes who may sign in, what a session grants, INV-001 or
     ADR-017.
* **Consequences**: an OIDC deployment must set one more variable
  (`VERITY_PUBLIC_URL`), already implied by `VERITY_OIDC_REDIRECT_URI`. A deployment
  that publishes the application on a different origin than it configures sends
  browsers to the configured one, which is the safe failure. A proxy no longer has
  to rewrite `Location` headers to make sign-in work.
* **Not decided here**: Supabase Auth's own redirect handling, which does not use
  these routes; whether other, non-authentication pages need the public origin
  (none build an absolute URL today); a separate canonical-origin check for
  Server Actions (Next's own origin check is unchanged).
* **Rejected**: trusting forwarded headers (the vulnerability above); keeping
  `request.url` and asking every operator's proxy to rewrite `Location`
  (undocumented, fragile and invisible when wrong); deriving the origin from
  `VERITY_OIDC_REDIRECT_URI` alone (it names a callback, not an origin, and is
  absent from a Supabase deployment); changing `HOSTNAME` (it is a bind address,
  and `0.0.0.0` is a listen wildcard).
* **Status**: `ACCEPTED` 2026-10-02 by the product owner ("Approve an explicit
  public-origin configuration"), implemented in the same change.
* **Related**: ADR-020 (OIDC browser identity: `VERITY_OIDC_REDIRECT_URI`,
  returnTo), ADR-031 (deployment modes), the object-storage F2 verification record
  (finding F6), `deploy/security/preflight.sh`.
