# Architectural Decision Record

## ADR-047: A BOM revision is a row with a lifecycle; a released revision is immutable; required quality gates fail closed

* **Decision ID**: ADR-047
* **Status**: PROPOSED (2026-10-18). Not accepted: it changes manufacturing behaviour for every tenant that
  installs the capability and adds a database-level guard, so it needs the product owner's decision before
  any migration is written (`CLAUDE.md` stop conditions).
* **Review, 2026-10-18**: **design direction accepted with the amendments below; the ADR stays PROPOSED**
  until its final text and cross-capability implications are reviewed. M1 is authorised only as a bounded
  extension of Task 118, and only after the stop/go checklist in `clients/dsew/phase1-design.md` section 12
  passes, including a backfill rehearsal on a copy of the DSEW demo tenant.
* **Amendments required before implementation**
  * A released revision is immutable. A change is a new revision with an attributable reason and release history.
  * An order keeps the exact released revision it was created against; a new release never rewrites existing orders.
  * Every transition and release goes through an authorised, audited command; the UI is never the only control.
  * Required quality checks are determined explicitly for the product or released configuration. A missing
    operation or checkpoint never means "quality passed".
  * Overrides need a specific permission, a reason and an audit event. **Define which gates may be overridden and
    which are never bypassable; there is no universal override.** (Open: the list of never-bypassable gates.)
  * Tenant isolation preserved: negative cross-tenant tests, and immutability verified through every application
    write path, with the database trigger as a backstop.
  * The stock balance projection gets a reconciliation test against the append-only ledger.
* **Question**: A first client (D & S Electric Works, `clients/dsew/`) needs drawings and bills of material to
  be controlled: which revision a job was built to must be provable, and a released revision must not change.
  Today a BOM has no lifecycle. How do revisions work without breaking existing orders, and how does a
  required inspection stop being skippable?
* **Context** (read and test-verified 2026-10-18, see `clients/dsew/gap-matrix.md`):
  * `manufacturing/bom.ts` has only `createBom`, `setBomActive` and `createOrderFromBom`. There is no edit
    command, so a BOM is effectively immutable; a changed recipe takes a new code with no link to the old.
    The three Prisma write sites are all in `bom.ts`; no raw SQL touches the table; no path edits
    `custom_fields` after creation. There is no database-level guard.
  * `createOrderFromBom` copies scaled lines onto the order and stores `bomId`.
  * `completeManufacturingOrder` only counts open operations; an order with no operations skips the QC gate,
    and a stage with no checkpoints completes freely. No override exists.
  * `inventory_stock_movement` is append-only by trigger and insert-only policy (read 2026-10-18).
* **Decision**:
  1. **One row, one revision.** `manufacturing_bom` keeps one row per revision, so `manufacturing_order.bom_id`
     already pins the exact revision. New columns: `family_code`, `revision`, `status`, `effective_from`,
     `change_reason`, `supersedes_id`, `released_at`, `released_by_id`, `submitted_by_id`. `code` stays the
     human reference. `active` keeps its meaning as the retire switch for a released revision.
  2. **Lifecycle** through the state runtime (ADR-009 categories): `draft` (Draft), `in_review` (Pending),
     `released` (Active), `superseded` (Completed), `withdrawn` (Cancelled). Only `released` and `active` may
     create an order. Releasing a revision supersedes the previous one in the same transaction. At most one
     `released` revision per family (partial unique index).
  3. **Immutability twice.** Command preconditions, and a database trigger that rejects any change to the
     structural columns or the lines of a non-draft revision, any delete of a non-draft revision by the
     application role, and any illegal status change. A privileged role may delete (tenant teardown cascades),
     mirroring `verity.reject_mutation`.
  4. **Revise, never edit.** Changing a released BOM means creating a new draft revision that copies the lines,
     with a mandatory change reason, then submit, approve (the `approval` capability, a separate permission)
     and release. Self-approval is refused by default; a tenant setting with an audited owner exception may
     allow it where the client has no second approver.
  5. **Backfill.** Every existing BOM becomes revision `A`, `released`, `family_code = code`. No order is
     touched.
  6. **Required gates fail closed.** The released revision may declare `requires_route` and required
     checkpoint keys. An order made from such a revision cannot be started without a planned route, and cannot
     be completed or dispatched until every required checkpoint has a current passing verdict. An order with
     no operations no longer bypasses a requirement the revision declares. A tenant or product that declares
     nothing keeps today's behaviour, so other clients are unaffected.
  7. **Override.** One command, `ActionExecute` on `verity.manufacturing.gate_override`, requires a dedicated
     permission and a reason of at least 10 characters, and writes an append-only `gate_override` row plus the
     activity record. No other path bypasses a declared gate.
* **Alternatives considered**
  * A separate `bom_revision` table with a header: cleaner naming, but every order, query and screen that uses
    `bomId` would change, and `bomId` would then need a second pointer. Rejected: churn without new capability.
  * Keep "a changed recipe takes a new code": loses lineage and approval and cannot express supersession.
  * Version only by the existing optimistic `version` integer: that is concurrency control, not revision control.
  * Enforce immutability in commands only: leaves a future code path or manual SQL able to change a released
    revision silently. Rejected: the guarantee is about records, so the database enforces it too.
  * Make the QC gate mandatory for every tenant: would change behaviour for clients that never asked for it.
    Rejected; the requirement is declared per released revision.
* **Rationale**: it makes the revision that built a job provable, keeps every existing screen and foreign key,
  and puts the guarantee where a bug or a hand-run script cannot bypass it.
* **Consequences**
  * Commands: `reviseBom`, `submitBom`, `approveBom`/`releaseBom`, `rejectBom`, `withdrawBom`; `createBom`
    creates a draft family revision A (existing tests and the seed must call release, or use a documented
    legacy path); `createOrderFromBom` requires `released` and active.
  * New state definitions and transitions, a permission set (author, release, override), activity entries.
  * Tests: lifecycle, immutability by command and by direct SQL as the application role, one released per
    family, order keeps its original revision after a newer release, fail-closed gate, override audit,
    cross-tenant negative tests.
  * Single-level BOM only. Multi-level BOM and formal engineering change orders are separate, estimated work.
* **Migration implications** (dry-run 2026-10-18 on a disposable copy of the local database, 3 BOMs, 18 lines,
  6 orders referencing a BOM): backfill left counts unchanged (3 / 18 / 6, no orphan orders); the migration
  reran without error; the application role was refused on every immutable path and allowed to retire a
  revision; a new draft revision could be edited, submitted, released with the previous one superseded in one
  transaction, and existing orders kept pointing at the superseded revision; the rollback script restored the
  original columns and row counts. A tenant delete as a privileged role still cascades through guarded rows.
  Production: backup first, maintenance window, apply as `postgres`; the dry-run used one small local dataset,
  so it is not evidence about production volumes.
* **What this is not**: not a change to INV-001, ADR-017 or `enforcePolicy()`; not a new platform primitive
  (it is a manufacturing capability change on top of the state and approval runtimes).
