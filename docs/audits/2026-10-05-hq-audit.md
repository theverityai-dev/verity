# HQ audit: what a platform operator console needs, and what Verity's HQ has (2026-10-05)

Status: **code pass done; live usability pass pending** (needs an operator session on
`app.theverityai.xyz`; the auditor does not sign in to production on anyone's behalf).

Authority for HQ's role: ADR-013 (Global HQ Operator Security Model), ADR-016 (scheduler may
enumerate tenants), ADR-021 (capability pins), ADR-022 (Industry Packs as signed artifacts), and the
target market in `docs/enterprise-readiness/msme-reference-workload.md` (many small tenants on one
deployment). Product-owner finding that started this: HQ is hard to use and understand, and is not
viable as an HQ.

## 1. What HQ is for

HQ is where the Verity team runs the business of hosting many small client businesses. Its users are
operators (founders, support, implementation staff), not the clients. Every job below is something an
operator must be able to do **without a developer, a database console or a seed script**.

## 2. Required capabilities

Priority: **P0** = HQ is not viable without it; **P1** = needed to run more than a handful of
clients; **P2** = needed at scale or for enterprise buyers.

| # | Job | Pri | What it needs |
|---|---|---|---|
| A1 | See every client and its health at a glance | P0 | Directory with status, modules, users, last activity, open problems, plan |
| A2 | Onboard a new client end to end | P0 | Guided flow: name, time zone, industry pack or template, modules, first admin invite, sample or imported data, "ready" checklist |
| A3 | Change a client's lifecycle state | P0 | Trial, active, suspended, offboarding, archived, with reason and audit; suspended clients cannot sign in |
| A4 | Give a client's admin access and fix access problems | P0 | Invite, resend invite, reset password, unlock, see who has access |
| A5 | Support a client from inside their workspace | P0 | "Enter client" with a stated reason, a visible banner while inside, time limit, and an audit entry the client can see |
| A6 | Know when something is broken | P0 | Per-client and platform-wide: failed commands, job and scheduler runs, undelivered events, integration errors, with drill-down |
| A7 | Turn modules on and off and configure them | P0 | Module catalogue with dependencies, readiness, and what turning it off does to data |
| B1 | Manage packs and templates | P1 | Industry pack catalogue (ADR-022), versions, which clients use which pack |
| B2 | Roll out upgrades safely | P1 | Capability pins per client (ADR-021), staged upgrade, see who is on which version |
| B3 | Plans and billing for Verity itself | P1 | Plan per client, seats, usage, invoices, overdue state linked to A3 |
| B4 | Platform usage and adoption | P1 | Active users, module adoption, clients going quiet (churn signal) |
| B5 | Data import, export and offboarding | P1 | Import on a client's behalf; full export for a leaving client (DPDP); deletion after retention |
| B6 | Operator team and roles | P1 | Invite operators, operator roles (support vs admin), least privilege, operator audit |
| B7 | Announcements and maintenance | P1 | Message one, some or all clients; schedule a maintenance window |
| C1 | Per-client security settings | P2 | SSO/OIDC config, password policy, API keys, IP rules |
| C2 | Compliance evidence | P2 | Exportable audit, access reviews, retention settings |
| C3 | Global search | P2 | Find a client, person or record across HQ |

## 3. What HQ has today (from code)

Routes: `/hq` overview, `/hq/clients` directory, `/hq/clients/[tenantId]` with tabs Overview,
Modules, Operations, Organizations, People, Roles, Settings; `/hq/audit`; `/hq/settings`.

| # | Status | Evidence |
|---|---|---|
| A1 | Partial | Directory and overview exist. `Tenant` has no status or plan field, so health can only be inferred from activity counts |
| A2 | **Thin** | `CreateClientForm` asks for name and time zone only. No pack, modules, first admin or readiness step in the flow; those are separate tabs the operator must know to visit |
| A3 | **Missing** | `Tenant` has no lifecycle state. A client cannot be suspended or offboarded from HQ |
| A4 | Partial | Invite, assign role, revoke, set person state exist (`verity.platform.*`). No resend invite or reset password from HQ found |
| A5 | Partial | `enterClient` exists. Reason capture, in-workspace banner and time limit not verified in code |
| A6 | Partial | Per-client Operations tab shows undelivered events, SLA clocks, sync exceptions, provider bindings, recent changes, security events. No platform-wide failure view, no scheduler/job run history, no failed-command list |
| A7 | Partial | Modules tab lists and toggles capabilities (`set_capability_state`). Dependency and data-impact explanation not verified |
| B1 | **Missing** | Packs exist in code (`pack.ts`, `pack-manifest.ts`) with no HQ screen |
| B2 | **Missing** | `capability-upgrade.ts` and pins exist with no HQ screen |
| B3 | **Missing** | No plan, seat or billing model for Verity's own clients |
| B4 | Partial | Overview shows clients, people with access, 30-day changes and security events. No active-user or adoption measure |
| B5 | **Missing** in HQ | Import exists inside a client workspace (`/import`); no export or offboarding |
| B6 | Partial | Settings lists operators. No invite-operator or operator-role screen found |
| B7 | **Missing** | |
| C1 | Partial | API key commands exist (`create_api_key`); OIDC is platform-level. No per-client security screen found |
| C2 | Partial | `/hq/audit` exists. Export and filters not verified |
| C3 | **Missing** | |

**Summary:** of the 7 P0 jobs, 1 is missing (A3), 1 is thin (A2) and 5 are partial. 5 of the 7 P1 jobs are missing outright.

## 4. Live usability pass (pending)

To be done in an operator session, each page judged on: can a new operator tell what it is for in five
seconds; is the next action obvious; are terms plain (not internal names like "provider bindings" or
"undelivered events"); empty, loading and error states; phone width; keyboard.

## 5. Recommended order

1. **A3 + A1:** add a client lifecycle state (needs a schema change and an ADR touch-point with
   ADR-013, since suspension affects sign-in) and show status in the directory.
2. **A2:** turn "create client" into a guided onboarding that ends with a ready client and an invited
   admin.
3. **A6:** one platform-wide "needs attention" view: failed commands, stale scheduler, undelivered
   events, sync exceptions, across all clients.
4. **A4/A5:** resend invite, reset password, and an audited support session with reason and banner.
5. Then B1, B2, B6, B3 in that order.

Items 1 and 4 touch security boundaries (sign-in, operator elevation) and per `CLAUDE.md` need their
design reviewed before code.
